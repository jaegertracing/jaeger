## Abstract

The ClickHouse backend creates its twelve tables and materialized views at startup from one `CREATE ... IF NOT EXISTS` template per object, and has no way to change an object that already exists. The first change to the schema since it reached users, the missing OTLP span columns of #9789, therefore has to establish how the schema is amended from now on. This RFC describes the mechanism as it stands, states what a replacement has to satisfy, and analyses five families of approach: versioned delta files applied by a migration framework, as #9789 sketched and #9796 implements with golang-migrate; the same deltas applied by a small in-house migrator; a full copy of the schema per version, which is how the Cassandra backend works; living templates for fresh installs with generated, reviewed deltas for upgrades, the workflow of Atlas and Prisma; and reconciliation, where the templates stay the single declarative description of the desired schema and the backend computes at startup the `ALTER` statements that bring the live database to it, in the manner of Kubernetes controllers and Terraform.

Reconciliation is the recommendation. It keeps today's per-object templates as the living source of truth, asks a contributor for no version number or frozen file, and gives operators who manage the schema themselves a printed plan of exactly what their database lacks. ClickHouse makes the diff tractable without a SQL parser: the desired tables are created under throwaway names beside the live ones and compared with them through the system catalogs, so both sides are normalized by the same server. At startup the backend applies only the additive part of the plan, new objects, columns and indexes, which is idempotent and commutes across concurrent instances and releases; every other change, a codec, default, setting, TTL or view query, is reported and applied by a one-shot operator command, because ClickHouse offers no primitive that can serialize such changes across instances safely. The engine reports and never executes a change that would rewrite data, never drops anything, and never fails a start over a difference it cannot resolve, so a binary restarts after an operator's runbook and a rollback restarts the previous release. A survey of third-party reconcilers for ClickHouse found none that is both embeddable and under a free license, so the diff engine is written in-house, informed by the designs of those tools. Release-time snapshots and numbered migration files are generated by the same engine rather than authored, for people who want a versioned audit trail.

## 1. Motivation

Three things force the question now.

1. **A schema change is pending.** #9789 adds ten columns to the `spans` table. Against an existing deployment the startup statements are no-ops, so without a migration mechanism the columns never appear and the writer fails on its first insert after the upgrade.
2. **RFC 0017 queues more.** The codecs, table settings and skip indexes that RFC 0017 adopts are each a metadata-only `ALTER TABLE`, and its `LowCardinality` wrappers are a column type change that rewrites data and needs an operator procedure (§2.3). The backend is going to change its schema several times in the next few releases, and each change needs a defined path.
3. **Two PRs already implement one answer.** #9796 and #9799 adopt golang-migrate along the lines sketched in #9789 and put the whole baseline schema in a single `000001_initial_schema.up.sql`. Review of those PRs showed that the file layout, the test design and the library's fit need deciding before the code, which is what an RFC is for.

The Cassandra backend is the cautionary example. Its schema lives in `v001.cql.tmpl` through `v004.cql.tmpl` under [`internal/storage/v1/cassandra/schema/`](../../internal/storage/v1/cassandra/schema/), each a complete copy of every table, and upgrades are operator-run shell scripts in a `migration/` directory that the binary knows nothing about. A change to one table meant copying the entire schema into a new file, and nothing recorded which version a running keyspace was at. Whatever ClickHouse adopts has to do better on both counts.

## 2. Current State

### 2.1 Files

The schema is twelve files under [`internal/storage/v2/clickhouse/sql/`](../../internal/storage/v2/clickhouse/sql/), one per object, each embedded as a string variable in `queries.go`:

| File | Object | Templated |
| --- | --- | --- |
| `create_spans_table.sql` | `spans` table | yes |
| `create_services_table.sql` | `services` table | yes |
| `create_services_mv.sql` | `services_mv` view | no |
| `create_operations_table.sql` | `operations` table | yes |
| `create_operations_mv.sql` | `operations_mv` view | no |
| `create_trace_id_timestamps_table.sql` | `trace_id_timestamps` table | yes |
| `create_trace_id_timestamps_mv.sql` | `trace_id_timestamps_mv` view | no |
| `create_attribute_metadata_table.sql` | `attribute_metadata` table | yes |
| `create_attribute_metadata_mv.sql` | `attribute_metadata_mv` view | no |
| `create_event_attribute_metadata_mv.sql` | `event_attribute_metadata_mv` view | no |
| `create_link_attribute_metadata_mv.sql` | `link_attribute_metadata_mv` view | no |
| `create_dependencies_table.sql` | `dependencies` table | yes |

The six table files are `text/template` documents rendered with `schemaTemplateParams` in `factory.go`:

```go
type schemaTemplateParams struct {
    TTLSeconds           int64  // zero renders no TTL clause
    MergeTree            string // ENGINE clause body for raw-row tables
    AggregatingMergeTree string // ENGINE clause body for derived tables
}
```

`TTLSeconds` comes from the `ttl` setting and renders `TTL start_time + INTERVAL n SECOND DELETE` on `spans` and `TTL end + ...` on `trace_id_timestamps`. The two engine strings come from the `table_engine` block that #9813 introduced: `merge_tree: {}` renders `MergeTree` and `AggregatingMergeTree`, and `replicated: {...}` renders `ReplicatedMergeTree('/path', 'replica')` and its aggregating counterpart. The materialized views are plain SQL because each writes `TO` its target table and carries no engine of its own.

### 2.2 Startup behavior

`newSchemaBuilder` holds the twelve statements in dependency order, tables before the views that read them, and renders the six templates. With `create_schema: true`, `NewFactory` executes the statements one by one over the native connection before serving traffic. With `create_schema: false`, nothing runs and the operator owns the tables.

Nothing is recorded about what ran. There is no version table, no fingerprint of the DDL, and no check at startup that the tables match what the binary expects. A mismatch surfaces as an insert or query error on the first request that touches the missing column.

### 2.3 What ClickHouse allows after `CREATE`

The shape of any migration mechanism follows from which parts of a table can change in place.

| Change | Statement | Cost | Replicated tables |
| --- | --- | --- | --- |
| Add a column | `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` | metadata only¹ | propagates through Keeper |
| Add a skip index | `ALTER TABLE ... ADD INDEX IF NOT EXISTS` | metadata only; existing parts are indexed on merge or by `MATERIALIZE INDEX` | propagates |
| Change a column's codec | `ALTER TABLE ... MODIFY COLUMN ... CODEC(...)` | metadata only; parts are re-encoded on merge | propagates |
| Replace a skip index | `DROP INDEX` then `ADD INDEX` | `DROP INDEX` is a mutation that only deletes index files; the new index is built on merge or by `MATERIALIZE INDEX` | propagates |
| Change a column's type, including adding `LowCardinality` | `ALTER TABLE ... MODIFY COLUMN ... <type>` | a mutation that rewrites every part² | propagates |
| Change a table setting | `ALTER TABLE ... MODIFY SETTING` | metadata only | replica-local³ |
| Change or remove TTL | `ALTER TABLE ... MODIFY TTL`, `ALTER TABLE ... REMOVE TTL` | a mutation by default; metadata only with `materialize_ttl_after_modify = 0`, after which the new expression applies as parts merge⁴ | propagates |
| Change a view's query | `ALTER TABLE <view> MODIFY QUERY` | metadata only; generally available since ClickHouse 23.11 | replica-local³ |
| Extend the sorting key | `ALTER TABLE ... MODIFY ORDER BY` | metadata only, and only by appending columns added in the same statement | propagates |
| Drop a column | `ALTER TABLE ... DROP COLUMN` | destroys data | propagates |
| Change `ENGINE`, `PARTITION BY`, or the existing sorting key | not possible | requires a new table and a copy | n/a |

- ¹ The column is added to each part's metadata; existing parts have no value for it and evaluate the default in force at read time until they are merged, so a later change to the default changes what those parts read (§5.4).
- ² A mutation is background work over every affected part, which for a large `spans` table is hours of I/O. It is the reason type changes are operator procedures rather than startup steps (§5.4).
- ³ A `MODIFY SETTING` on a `Replicated*` table changes only the replica that received it, which the server's own code states (`StorageReplicatedMergeTree::alter` does not replicate a settings-only alter) and the documentation does not; a materialized view has engine `MaterializedView`, not a `Replicated*` engine, so its `MODIFY QUERY` is local too. Reaching every replica needs the fan-out of §2.4.
- ⁴ With materialization off, existing parts keep their rows until a merge re-evaluates the TTL, which is the behavior a day-partitioned table with `ttl_only_drop_parts` wants anyway.

Replication covers less than it seems. A column, index or codec `ALTER` on a `Replicated*` table is recorded in Keeper and applied on every replica, so a statement issued through one connection reaches the whole shard. A `CREATE TABLE`, a `MODIFY SETTING` and a view's `MODIFY QUERY` are local to the server the client reached, and reaching the others needs `ON CLUSTER`, a database with the `Replicated` database engine, or a connection to each. §5.6 draws the consequence.

### 2.4 Facilities ClickHouse offers a schema tool

- **System catalogs.** `system.tables` has `engine_full`, `sorting_key`, `partition_key`, `create_table_query` and, for views, `as_select`; `system.columns` has each column's `type`, `default_kind`, `default_expression`, `compression_codec` and `position`, with `Nested` groups flattened to `events.name Array(String)`; `system.data_skipping_indices` has each index's `type_full`, `expr` and `granularity`. Everything a diff needs is a query away, normalized by the server.
- **Scratch tables.** `CREATE TABLE` of an empty table is cheap, so the desired DDL can be created under a throwaway name and compared with the live objects through the catalogs above, which avoids writing a ClickHouse DDL parser; `formatQuerySingleLine` reprints a `SELECT` the way `as_select` stores it, which does the same for views. The scratch tables have to be ordinary persistent tables: a session-scoped `CREATE TEMPORARY TABLE` would need no cleanup, but on ClickHouse 25.12 a temporary `MergeTree` table reports empty `sorting_key`, `partition_key` and `engine_full` in `system.tables` and none of its indexes in `system.data_skipping_indices`, so only its columns could be compared.
- **A cross-process lock.** ClickHouse has no advisory locks, but an `INSERT` into a `KeeperMap` table issued with the query setting `keeper_map_strict_mode = 1` fails when the key exists, which is a compare-and-set with Keeper as the arbiter. It needs ClickHouse 23.4 or later, where `keeper_map_strict_mode` arrived, a Keeper ensemble, and the opt-in `keeper_map_path_prefix` server setting, which no default configuration sets; a server without it refuses to create the table with `BAD_ARGUMENTS`. The strict-mode failure itself surfaces as `KEEPER_EXCEPTION` (error 999) with a "Node exists" message rather than a code of its own, which is what the lock has to match on.
- **DDL fan-out.** The `Replicated` database engine replays every DDL statement issued to one replica on all of them, and is the default on ClickHouse Cloud; `ON CLUSTER <name>` does the same per statement on a self-hosted cluster with an ordinary `Atomic` database.

### 2.5 How the other backends do it

Cassandra is covered in §1. Elasticsearch and OpenSearch have no comparable problem: their mapping is an index template that the binary installs at startup, and because indices roll, by day or by alias rollover, a new mapping applies to the next index without altering the previous one. Badger and memory have no persistent schema.

## 3. Requirements

The mechanism is judged against these criteria, which also form the rows of the comparison in §4.6.

1. **Per-object deltas.** A change to one column of one table is a change to one short file, never a copy of the schema.
2. **One source of truth.** What a fresh install creates and what an upgraded install ends up with derive from one set of files, not two paths kept equal by discipline.
3. **Template parameters survive.** `ttl` and `table_engine` are properties of the deployment, not of the schema, and every `CREATE` has to render them. A replicated deployment that gets local tables because a migration file hard-codes `MergeTree` is a silent data-loss configuration.
4. **The database's state is knowable.** The binary can tell what the live schema lacks, and an operator can tell what a cluster has.
5. **Safe with concurrent instances.** Several Jaeger instances start together against one database. The result has to be correct whoever finishes second.
6. **Operator-managed schema stays possible.** With `create_schema: false` the operator applies the DDL by hand, and the binary gives them exactly what to apply.
7. **Readable current schema.** A developer changing the writer can find out what the `spans` table looks like today by reading a file, not by replaying history.
8. **Small dependency footprint.** The backend pulls in no database drivers or connection paths it does not otherwise use.
9. **Little bookkeeping imposed on contributors.** Version numbers, ordering rules, frozen files and generated golden files are each a thing a contributor has to learn and a reviewer has to check.
10. **What runs in production is reviewable.** A reviewer of a schema PR, and an operator before an upgrade, can see the statements that will execute.
11. **Operator customizations survive.** An index, column, codec or setting an operator added by hand is not undone by an upgrade.
12. **Planning writes nothing.** Computing what the database lacks changes no live object and needs no privilege beyond reading the catalogs; privileges a plan does need are stated.

## 4. Approaches

### 4.1 Versioned deltas applied by a migration framework

This is the model of Flyway, Liquibase, golang-migrate and goose, and the one #9789 sketched: a numbered sequence of forward-only files, a table recording which have run, and a library that applies the pending ones in order. The current schema is the sum of the files, so the baseline is version 1 and every change is a new file. #9796 implements it with golang-migrate.

Two properties of golang-migrate bear on the choice. The layout is free: the library reads each version as one `io.Reader` from any `fs.FS`, so per-object files can be rendered and concatenated in memory, and the single baseline file in #9796 is a choice rather than a constraint. The ClickHouse driver is a poor fit for this backend: it needs a second connection through `database/sql`, its process-local lock leaves concurrent instances to idempotence alone, and its version-table handling and its refusal to start against a newer recorded version each contradict a requirement of §3. The specifics were raised in the review of #9796 and are not repeated here; what remains of the library once they are worked around is the version table and the ordered walk, about a hundred lines.

### 4.2 Versioned deltas applied by an in-house migrator

The same layout, one directory per version holding one file per object the version changes, with the walk and the version table written in the backend over the native connection. The driver problems above disappear, and the cross-version interleaving of concurrent instances remains, needing either the `KeeperMap` lock of §2.4 or a rule that a version never reassigns a property an earlier version assigned.

The bookkeeping stays: version numbers, a frozen baseline that is no longer the readable schema, a golden `SHOW CREATE TABLE` dump to read instead, a rule that a released version is never edited, and the ledger's own upkeep, which is a checksum per applied file so that an edited released version is detected, and a baseline step that records version 1 for the databases `create_schema: true` created before the ledger existed, detected from the presence of `spans`.

### 4.3 Full copy of the schema per version

The Cassandra model. Each version is a complete, readable schema, and the diff between two versions is whatever a human writes into a migration script. It fails requirement 1 by construction and records nothing in the database, and is listed because it is the precedent in this repository.

### 4.4 Living templates for fresh installs, deltas for upgrades

Keep today's templates as the readable current schema and use them for a fresh install, recording the newest version number without running the deltas; an existing database applies the deltas, which a PR commits alongside its template edit. This is the model Atlas calls the versioned workflow with `atlas migrate diff`, and Prisma and Alembic practice too: the contributor edits the declarative schema, a tool diffs it against the previous state in a throwaway database and writes the numbered migration file, and the contributor reviews and commits that file rather than writing it. In its strongest form the runner applies only additive deltas at startup and leaves the rest to an operator command, exactly as §5 does, and CI checks parity by creating one database from the templates and one from each released snapshot plus the pending deltas and comparing the two through the catalogs. Both the generation step and the parity check are the catalog diff of §5.2, so the diff engine is built under this option too; what differs is that production executes statements a reviewer read in the PR, rather than statements computed against the live catalog. The costs are requirement 2, because a template edit whose generated delta was not regenerated after a later edit is caught only by the CI check, and the version record, ordering rules and ledger upkeep of §4.2, which a trunk-deployed fleet with concurrent PRs has to assign without a release number.

### 4.5 Reconciliation

Describe the desired schema once, declaratively, and let the tool compute the statements that bring the live database to it. This is how Kubernetes controllers treat resources, how Terraform treats infrastructure, and how Atlas, Skeema, sqldef and Prisma treat relational schemas. For ClickHouse specifically it is the model of Atlas's ClickHouse driver, PostHog's `chschema`, Noibu's `housekeeper` and the `diff` command of the Python `clickhouse-migrations`. Those tools run from a CLI at deploy time. The form in which a reconciler runs inside the application at startup is established too, under the constraint that it only ever adds: Ent's `Schema.Create` and GORM's `AutoMigrate` inspect the live database and issue `CREATE TABLE`, `ADD COLUMN` and `ADD INDEX` for what the Go schema has and the database lacks, and neither drops a column or index unless the caller passes an explicit option, because a reconciler that converges exactly would read a rename as a drop plus an add and an older binary would drop the columns a newer one added. The design below is that additive form.

For this backend the desired schema is today's twelve templates, unchanged and still edited in place. At startup the backend renders them, creates each table under a throwaway name in the same database, reads both the scratch and the live objects from the system catalogs, and diffs them per object. The diff vocabulary is the rows of §2.3 that do not rewrite row data and that apply to any existing table, which excludes `MODIFY ORDER BY`, since it only appends columns added in the same statement: `ADD COLUMN`, `ADD INDEX`, `DROP INDEX` followed by `ADD INDEX` to replace one, `MODIFY COLUMN ... CODEC`, `MODIFY SETTING`, `MODIFY TTL`, `MODIFY QUERY`, and `CREATE` for an object that does not exist. A TTL difference is applied without materializing it, so it takes effect as parts merge. Anything else the diff detects, a type change, a different sorting key, partition key or engine family, is reported and refused, because each is a mutation or a rebuild. Anything present in the live table and absent from the desired schema is left alone, because drop versus rename is undecidable from a diff and either loses data. The plan is a list of statements; with `create_schema: true` the backend applies its additive part at startup, with `create_schema: false` nothing runs at startup, as today, and a command prints and applies the plan on demand.

Two properties follow that no versioned design has. The templates are the single readable source of truth, and a contributor's PR is the template edit alone, with no number to assign and no file to freeze. And a database that drifted, because an operator added an index by hand or an earlier version of the binary created a table slightly differently, is reconciled toward the desired state rather than assumed to match a version number.

A versioned audit trail is a product of the same engine rather than its input: at release time, diffing the previous release's rendered schema against the current one through scratch tables yields a numbered migration file to commit, for people who want one.

#### Third-party reconcilers for ClickHouse

The engine, with its verification step, is several hundred lines, so a library was looked for first. None is both embeddable in a Go binary and under a free license.

| Tool | Desired-state input | Diff method | License | Embeddable |
| --- | --- | --- | --- | --- |
| Atlas | HCL or SQL | live introspection, plan | Apache 2.0 core; the ClickHouse driver is in the paid Pro tier | ❌ |
| PostHog/chschema | HCL | live introspection, `diff -sql`; flags engine, `ORDER BY` and `PARTITION BY` changes as unsafe | MIT | ❌ Go, but all code under `internal/`, CLI only |
| Noibu/housekeeper | SQL DDL file | generates `ALTER`s, `ON CLUSTER` | GPL-3.0 | ❌ license |
| anytoe/chsync | live or `.sql` snapshot | catalog diff | MIT | ❌ Go under `internal/`; no indexes, codecs or TTL; self-described as not battle-tested |
| zifter/clickhouse-migrations 0.14 | `schema.sql` | scratch database plus catalog diff; refuses engine, `ORDER BY`, `PARTITION BY`, `SETTINGS`; comments out drops unless `--allow-destructive`; `KeeperMap` lock | MIT | ❌ Python |

Two of these matter as prior art even though none is adopted. The Python tool diffs through throwaway objects and the catalogs as §5 proposes and refuses the same class of changes, which is independent evidence that the method works on ClickHouse, and it implements the `KeeperMap` lock of §2.4. `chschema`'s unsafe-change classification matches §2.3.

- ¹ The library reads each version as one stream, so per-object files can be concatenated in memory; the single baseline file in #9796 is that PR's choice, not the framework's.
- ² Templates and deltas are two descriptions kept equal only by the CI parity check described in §4.4, which is the §5.2 diff run against two databases.
- ³ As #9796 stands it renders the baseline through the templates; the earlier shape its review commented on hard-coded the engine.
- ⁴ A version number, which says what was recorded, not what the tables contain; drift is invisible.
- ⁵ The plan is computed from the live catalog, so what is reported is what the database actually lacks.
- ⁶ The library's version table creation is not idempotent, so first starts race, and pending versions can interleave across instances.
- ⁷ Correct if every statement is idempotent and no version reassigns an earlier version's property; a `KeeperMap` lock would make it 🟢.
- ⁸ Startup applies only additive statements, which are idempotent and commute up to a difference that the next plan reports (§5.5), so no coordination is needed. Non-additive statements run only from a one-shot operator command. Option 4.4 in the strongest form of its description shares this; its version record is one more write, made idempotent by inserting a row per version rather than updating one.
- ⁹ The operator receives "versions 2 and 3 are pending" and the files, and is trusted to apply them whole.
- ¹⁰ The operator receives the exact statements their database lacks, computed against it.
- ¹¹ Through a generated golden dump rather than the authored files.
- ¹² A second `database/sql` connection for the library's driver.
- ¹³ A contributor edits the template and nothing else; the release snapshots of §5.7 are generated, not authored, and the database state is read, not recorded.
- ¹⁴ The PR shows the template edit, not the `ALTER`; the statements are visible in the release-time migration file (§5.7) and in the printed plan.
- ¹⁵ A delta touches only what it names, but a `MODIFY COLUMN ... CODEC` or `MODIFY SETTING` delta overwrites a customization of that property as surely as a computed one does.
- ¹⁶ Nothing present live and absent from the template is ever removed; a customized codec, setting or default is a deferred difference that every plan reports and that `apply` overwrites, so an operator who customizes one keeps it by not running `apply`, or by carrying the customization into the template.
- ¹⁷ A plan creates and drops scratch tables in the configured database (§5.2), which needs `CREATE TABLE` and `DROP TABLE` there; it never touches a live Jaeger object. Temporary tables would avoid the writes but lose the properties the diff compares (§2.4).
- ¹⁸ The delta is generated by the diff engine and reviewed rather than written; the version number, the ordering rule, the frozen-file rule and the ledger upkeep of §4.2 remain.
- ¹⁹ The full copy and the human-written migration script that takes a database from the previous copy to it are two descriptions, and nothing checks them against each other.

Reconciliation is the recommendation, and 4.4 is the alternative it is weighed against, because the two share the diff engine, the additive-only startup and the operator command and differ in one thing: whether production executes statements computed against the live catalog or statements the same engine computed at PR time against the previous release and a reviewer read. The rows that decided it are 4, 6, 7 and 9: the plan is computed from what the database actually contains, the operator gets the exact statements they lack, the templates stay the readable schema, and contributors learn no numbering or freezing rules, which for a fleet deployed from trunk means no ordering problem to solve at all. The rows it loses are 12, scratch tables and the two grants they need, and code to own, catalog comparison plus a verification step, a shape the prior art shows to be solved; row 10 is recovered by the release-time migration files and the printed plan.

The objection to computing statements in production is that a live difference has no label: an operator's customization, an upgrade that stopped halfway and a schema the previous release created look the same in the catalog, and a delta that names its change needs no such label. The design answers it by never interpreting a difference. Each compared property maps to one fixed action in the table of §5.2, additive statements are applied, deferred ones reported and the rest refused, and nothing live is ever removed, so the three cases are all reported in the same words and resolved by the same operator, who under 4.4 would not learn of them at all. What remains of the objection is real: the diff engine is the production path, so a defect in it is a production defect rather than a CI failure, and the mitigation is that the compared properties are a closed list tested row by row (§5.9), that startup executes only the three additive statement kinds, and that 4.4 is the fallback if the engine proves harder than estimated, since it needs the same engine for its generation and parity steps, shares the per-object layout and the idempotence rules, and adds the version record.

## 5. Design

### 5.1 Desired state

The twelve files stay where they are and keep their names. They remain the complete description of the desired schema, edited in place when the schema changes: the OTLP columns of #9789 are ten lines added to `create_spans_table.sql`, and RFC 0017's codecs are edits to the same file. The templates are rendered with `schemaTemplateParams` as today.

### 5.2 The reconciler

```go
// schemaReconciler computes and applies the statements that bring the live schema
// to the rendered templates.
type schemaReconciler struct {
    conn   driver.Conn
    params schemaTemplateParams
}

// plan renders the desired tables under scratch names, reads both scratch and
// live objects from the system catalogs, and returns the statements that would make
// the live objects match, in template order so that a table is created or altered
// before the views that read it.
func (r *schemaReconciler) plan(ctx context.Context) (schemaPlan, error)

// apply executes the statements of a plan in order. Refusals are reported by the
// caller; they never gate the statements the plan can execute.
func (r *schemaReconciler) apply(ctx context.Context, p schemaPlan) error

type schemaPlan struct {
    Statements []string         // CREATEs and metadata-only ALTERs, in template order
    Refused    []schemaRefusal
}

type schemaRefusal struct {
    Object    string
    Reason    string // e.g. "column duration: type Int64 differs from UInt64"
    Statement string // what an operator would run, for the message
}
```

`plan` does the following, all through the native connection the factory already holds:

1. Open a client of its own with one connection to a single address, trying the configured addresses in turn until one answers, because the factory's `driver.Conn` is a pool over every configured address and scratch objects created through one transport are not visible through another server's. Render each table template with `TablePrefix` set to `_jaeger_scratch_<random>_` and the local engine family regardless of `table_engine`, so that a plan needs no `table_engine` to compute, and create the scratch tables in the configured database with a `COMMENT` that carries a fixed marker and this run's identity, which is what makes a scratch table recognizable as one. The templates gain `{{ .TablePrefix }}` in front of each table name for this, which renders empty for the live schema. A scratch table needs `CREATE TABLE` and `DROP TABLE` on the configured database; a grant that covers only `CREATE TABLE`, which today's `create_schema: true` gets by with, has to gain `DROP TABLE`, and §6 lists that. Inside a `Replicated` database the scratch DDL replicates like any other, which costs a few metadata round trips, and because such a database may be configured to accept only `Replicated*` engines, scratch tables there are rendered with the argument-less `Replicated*` engine that the database completes. Views are not created in scratch: a view's query is normalized with the server's `formatQuerySingleLine` function instead, which reprints the template's `SELECT` the way `as_select` stores it.
2. For each desired table, read `system.tables`, `system.columns` and `system.data_skipping_indices` for the scratch and the live copy; for each view, read `system.tables.as_select` and `create_table_query` of the live view. ClickHouse qualifies table references with the database at `CREATE` time, so the live `as_select` is compared with the qualifier of the configured database stripped, and the scratch prefix is stripped from the scratch side. A first-level `Nested` group is flattened to one `Array` column per member on both sides; a `Nested` group inside another, such as the attribute groups under `events` and `links`, stays one column of type `Array(Nested(...))`, so a change inside it is a type change.
3. Per object, compute the difference. A live object that is missing yields its rendered `CREATE` with the deployment's engine. A missing column yields `ADD COLUMN IF NOT EXISTS` placed `AFTER` its predecessor; a missing index yields `ADD INDEX IF NOT EXISTS`; an index whose `type_full`, `expr` or `granularity` differs yields `DROP INDEX IF EXISTS` followed by `ADD INDEX`; a codec difference yields `MODIFY COLUMN ... CODEC`, or `MODIFY COLUMN ... REMOVE CODEC` when the desired column has none; a setting difference yields `MODIFY SETTING`; a TTL difference yields `MODIFY TTL ... SETTINGS materialize_ttl_after_modify = 0`, or `REMOVE TTL` when the desired schema has none; a default expression difference yields `MODIFY COLUMN ... DEFAULT`; a view whose `as_select` differs yields `MODIFY QUERY` with the query text taken from the rendered template. The table under "What is compared" below is the complete list of properties compared and of what each difference yields; a difference with no statement is a refusal. Columns and indexes present live and absent from the desired schema yield nothing. Statements are applied in two passes, every table's first and then every view's, with `plan` run again between them and after them, up to three rounds, because two releases that both found a table missing both plan only its `CREATE`, and the one whose `CREATE` lost still has columns to add before its views can select them.
4. Drop this run's scratch tables, also on error. A crashed run leaves its tables behind, and the next run drops those that carry the marker comment and a `metadata_modification_time` more than an hour old; a table with the prefix and no marker belongs to someone else and is never touched. A run that finds one of its own scratch tables gone, because it was paused for over an hour and swept, fails its plan with an error and the start is retried; it never reads the absence as a missing object. The sweep is therefore bounded to one failed start in a case that needs an hour-long pause, which is the ownership guarantee the prefix alone could not give.

#### What is compared

The comparison is defined per object kind over the catalog columns below. A property not in this table is not compared, so an empty plan certifies exactly these properties and nothing else.

| Object | Property | Source | On difference |
| --- | --- | --- | --- |
| table | exists | `system.tables` | `CREATE` with the engine `table_engine` renders (additive); a refusal naming the setting when the configuration has none, because the reconciler never guesses an engine |
| table | engine family (`MergeTree`, `AggregatingMergeTree`) after stripping `Replicated` or `Shared` | `system.tables.engine` | refusal |
| table | replication mode against `table_engine`, when the configuration sets it: a local engine under `replicated`, or a `Replicated*` engine under `merge_tree`, is a mismatch; `Shared*` satisfies either, because ClickHouse Cloud substitutes it for both | `system.tables.engine` | refusal |
| table | sorting key, partition key, primary key, sampling key | `system.tables` | refusal |
| table | TTL clause, the text of `engine_full` between `TTL` and `SETTINGS`, which the server prints in a fixed order on both sides | `system.tables` | `MODIFY TTL` or `REMOVE TTL` (deferred) |
| table | constraints and projections | none declared by a template today; a template that declares one is a refusal until the comparison learns the property | refusal |
| table | settings, the `key = value` list of `engine_full` after `SETTINGS` | `system.tables` | `MODIFY SETTING` (deferred); the settings ClickHouse rejects with `READONLY_SETTING`, `index_granularity` and `index_granularity_bytes` among them, are a refusal, from a list kept in the code because the catalog does not mark them |
| column | exists | `system.columns` | `ADD COLUMN IF NOT EXISTS ... AFTER` (additive) |
| column | type | `system.columns.type` | refusal |
| column | default expression, for the plain `DEFAULT` kind | `system.columns` | `MODIFY COLUMN ... DEFAULT`, or `REMOVE DEFAULT` when the template has none (deferred, and subject to rule 4 of §5.4) |
| column | default kind | `system.columns.default_kind` | none and `DEFAULT` convert into each other through the row above; any transition involving `MATERIALIZED`, `ALIAS` or `EPHEMERAL` is a refusal |
| column | codec | `system.columns.compression_codec` | `MODIFY COLUMN ... CODEC`, or `MODIFY COLUMN ... REMOVE CODEC` when the template has none (deferred) |
| index | exists | `system.data_skipping_indices` | `ADD INDEX IF NOT EXISTS` (additive) |
| index | `type_full`, `expr`, `granularity` | `system.data_skipping_indices` | `DROP INDEX` then `ADD INDEX` (deferred) |
| view | exists | `system.tables` | `CREATE MATERIALIZED VIEW IF NOT EXISTS` (additive; a view carries no engine, so it needs no `table_engine`) |
| view | `TO` table | `create_table_query` | refusal |
| view | query, the template's `SELECT` through `formatQuerySingleLine` against the live `as_select` | `system.tables.as_select` | `MODIFY QUERY` with the template's text (deferred) |

Deliberately not compared: the Keeper path and replica name of a `Replicated*` engine, because deployments legitimately carry paths no template reproduces; a view's declared columns, which follow from the query that is compared; the position of existing columns; comments; and any column, index, projection or constraint present live and absent from the template, which an operator may have added and the reconciler never removes. Database qualifiers are stripped only where they name the configured database, so a deliberate cross-database reference would survive. `Nested` groups are flattened the same way on both sides, and a `Nested` group inside another is one `Array(Nested(...))` column, so a change inside it is a type difference.

The engine is never changed, because ClickHouse cannot change it in place (§2.3); the two engine rows exist to catch a configuration that disagrees with the tables, `table_engine.replicated` over local tables or `merge_tree` over replicated ones, with `SharedMergeTree` counting as replicated because ClickHouse Cloud stores every `MergeTree` table that way.

#### Additive and deferred statements

Statements fall into two classes, and the class decides who runs them.

- **Additive**: `CREATE ... IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`, `ADD INDEX IF NOT EXISTS`. Each is idempotent, and two such statements for the same object from different releases either agree or leave the one that ran first in place, after which the other definition shows up on the next `plan` as a deferred difference, or as a refusal if the two releases disagree on a type, which rule 2 of §5.4 forbids a release to do; nothing is lost and nothing is silently certified. Additive statements therefore need no coordination, and startup applies them.
- **Deferred**: `MODIFY COLUMN`, `MODIFY SETTING`, `MODIFY TTL`, `REMOVE TTL`, `DROP INDEX` plus `ADD INDEX`, `MODIFY QUERY`. These do not commute: an older release's `MODIFY QUERY` landing after a newer one's computes derived rows with the wrong query until someone notices, and an older TTL can expire parts in the meantime. ClickHouse has no primitive that lets concurrent instances order such statements safely: a distributed DDL that outlives its lease keeps executing, a `Replicated` database retries remote DDL until it completes, and a lock cannot revoke queued work. Deferred statements are therefore never applied at startup. They are reported, and applied by the one-shot operator command of §5.8, which an operator runs from one place at a time, or by startup under the opt-in `apply_deferred_changes: true`, which a deployment sets only when it guarantees by construction that a single instance reconciles, such as a single-node installation; a per-pod init container is not such a guarantee, because a rolling deployment runs the old and the new release's init containers at the same time.

### 5.3 Startup behavior

| `create_schema` | Plan | Behavior |
| --- | --- | --- |
| `true` | empty | Start. |
| `true` | additive statements, possibly with deferred ones and refusals | Apply the additive statements, verify them (§5.6), log the deferred statements and the refusals with the operator command that applies or shows them, and start. With `apply_deferred_changes: true`, apply the deferred ones too. |
| `true` | only deferred statements and refusals | Log them and start; with `apply_deferred_changes: true`, apply the deferred ones, verify them, and start. |
| `true` | cannot be computed | Fail: creating the schema was asked for and needs the privileges to plan it. |
| `false` | not computed | Start, as today. Nothing is created, read or dropped at startup; `clickhouse-schema plan` computes the plan on demand, with whatever user has the privileges. |

Startup fails for exactly three reasons: the plan could not be computed, an additive statement failed to apply, which includes a Jaeger user without the `ALTER` grant, or the verification of §5.6 found one still outstanding. The last two mean a column this binary writes is missing somewhere, which is the one difference that stops the binary from working. A refusal is a difference the reconciler cannot resolve, not evidence that the binary cannot run: a column an operator's runbook changed to `LowCardinality(String)` is still written by a binary whose template says `String`, and the previous release restarted during a rollback sees its template differ from a schema the newer release expanded. Failing either start would make every runbook a one-way door, so refusals are reported at every start and gate nothing. The one discrepancy a refusal reports that does affect the binary, a table whose engine disagrees with `table_engine`, is a configuration error the operator fixes in the configuration, and the log says so.

A deployment on the previous release has nothing to bootstrap: the first start with this mechanism computes a plan against its tables like any other.

### 5.4 Rules for changing the schema

1. **Expand only.** A template edit adds columns, indexes, codecs and settings or changes a view's query. It never removes or renames a column that the previous release reads or writes; removal is a template edit in the release after the one that stopped using it, and even then the reconciler does not drop it, so an operator runbook does. A rolling deploy therefore always has an older binary running against a schema that is a superset of what it expects, which `INSERT` with an explicit column list and `SELECT` with explicit columns already tolerate.
2. **No data-rewriting changes at startup.** A column type, including `LowCardinality` and any change inside the nested attribute groups of `events` and `links`, a sorting key, a partition key and an engine are changed by operator procedures with runbooks. A TTL change is a deferred statement that runs without materialization (§2.3). A template edit that changes one of them is legitimate for fresh installs, and the reconciler reports it as a refusal against existing databases at every start until the runbook has run, so the PR that makes the edit ships the runbook, and the test in §5.9 that reconciles from every prior release fails until it does. The runbook has to leave the previous release able to write the table, because that release restarts during a rollback and because the refusal does not stop it (§5.3): widening a type to `LowCardinality` or `Nullable` satisfies that, narrowing one does not.
3. **A view change is forward-only and must leave old rows valid.** `MODIFY QUERY` and `CREATE` of a missing view affect rows inserted from then on and repair nothing already in the target table. A view edit may therefore add derived columns, which old rows carry at their defaults, or change the query where existing target rows stay correct under the new definition. A change to grouping, filtering or aggregation that makes old rows wrong is not a template edit on its own: it ships with a backfill runbook that repopulates the target from `spans`, and the PR says so. Because `MODIFY QUERY` is deferred, a feature that depends on the changed view is not enabled by a successful start; its release notes say that `clickhouse-schema apply` is the prerequisite. Never drop-and-recreate a view, because inserts during the gap would bypass it.
4. **Defaults are semantics, not metadata.** A new column takes its type default, so an `INSERT` from a binary that does not know the column still succeeds. A change to an existing column's `DEFAULT` is metadata-only to execute and still changes data as read: parts written before the column existed hold no value for it and evaluate the current default, so after the change a row in such a part reads the new default while a row in a part that materialized the column keeps the old one, and the value of one row depends on its part's history. A default change is therefore acceptable only when every such row is correct under the new default, or it ships with `ALTER TABLE ... MATERIALIZE COLUMN` in a runbook that runs before it; the deferred `MODIFY COLUMN ... DEFAULT` of §5.2 executes the change, it does not certify it.

### 5.5 Concurrency

Startup applies only additive statements (§5.2), each idempotent, in template order. Concurrent instances of one release produce the same schema: a duplicate `ADD COLUMN IF NOT EXISTS` is a no-op, and on a `Replicated*` table reached through two replicas at once it can instead fail with `CANNOT_ASSIGN_ALTER` (error 517, "metadata on replica is not up to date"), which ClickHouse documents as retryable; without a retry the losing statement leaves its column absent, so every additive statement is retried with backoff on that error for up to a minute, and the retry is what makes the statement idempotent across replicas rather than a precaution. A start that exhausts the retries fails, and the next start plans again. Concurrent instances of two releases produce the union of their additive statements; where the two releases define a new column or index differently, the first definition stands and the second appears in every later `plan`, as a deferred difference for a codec, default or index definition and as a refusal for a type, so the disagreement is visible rather than resolved by chance. Additive statements commute up to that visible difference, which is what footnote 8 of §4.6 claims and no more. This is the whole concurrency story for startup, and it holds without a lock, a version table or a clock. It also bounds what a fleet pays for it: every statement startup issues is metadata-only, the scratch tables are empty, and the retry is capped, so a readiness probe sees seconds of schema work, not a mutation, unless an additive statement arrives while an operator's mutation is running on the same table (§5.6), and a fleet that wants no schema work in its pods at all runs `clickhouse-schema apply` as one pre-upgrade job (§5.8) with `create_schema: false` in the pods, which is also the least-privilege configuration, since the pods then need only `INSERT` and `SELECT`.

The operator command that applies deferred statements is meant to run once, from one place. As a guard rail against two operators running it at once, it takes a lock on a server that offers `KeeperMap` (§2.4): a `jaeger_schema_lock` table with one row keyed by the database name whose value is the holder's identity and a lease expiry, every mutation of which runs with `keeper_map_strict_mode = 1` and a predicate on the current value, so acquisition, renewal, takeover of an expired lease and release are each a compare-and-set that fails rather than overwrites. A mutation whose predicate matches no row succeeds as a no-op, so the command reads the row back after every mutation and holds the lease only while the row names its own identity; a read-back naming another holder means the mutation did not take effect and the command stops. The lock serializes the command's own statements; it cannot revoke distributed DDL that a previous holder queued, which is why it is a guard rail and the single-run instruction is the guarantee. Where `KeeperMap` is unavailable the command says so and runs unlocked.

### 5.6 Replicated clusters

The plan is computed against the replica the connection reached. Column, index, codec and TTL `ALTER`s on `Replicated*` tables propagate through Keeper; `CREATE`, `MODIFY SETTING` and a view's `MODIFY QUERY` are local to that replica (§2.3). A deployment with more than one replica therefore needs DDL fan-out. The alternative, each replica being repaired by whichever instance connects to it next, works only while the replica's Keeper metadata equals the current template: `CREATE` of the template against metadata that differs from it in anything, an operator-added column, a codec still deferred or a column the template has and the metadata lacks, fails with `INCOMPATIBLE_COLUMNS`, so it is not a mechanism to rely on. ClickHouse offers two fan-out mechanisms, and they are mutually exclusive.

- **A `Replicated` database**, the ClickHouse Cloud default and an option self-hosted, replays every DDL statement on every replica. The reconciler detects it from `system.databases.engine` and issues DDL with `distributed_ddl_output_mode = 'throw_only_active'`, which waits for the replicas that are up and surfaces a failure on any of them, instead of `throw`, which waits the full `distributed_ddl_task_timeout` for a replica that is down. Such a database rejects `ON CLUSTER` with a name other than its own, and since ClickHouse 24.9 it rejects `Replicated*` engines with explicit arguments by default, through `database_replicated_allow_replicated_engine_arguments`, so in that deployment `table_engine.replicated` is used without `keeper_path`, `replica_name` or `cluster`, and the database supplies the replication arguments. The cluster such a database registers under its own name, which the verification of this section reads through, connects with the credentials of the named collection in the database's `collection_name` setting and, without one, as `default` with no password, so a self-hosted `Replicated` database whose `default` user has a password needs that collection with `cluster_username` and `cluster_password` before the verification can read the other replicas; #9813 made those two fields optional so that the server's `default_replica_path` and `default_replica_name` apply when they are absent, which is the same rendering.
- **`ON CLUSTER`**, for a self-hosted cluster with an ordinary `Atomic` database. The backend adds an optional `cluster` field to `table_engine.replicated`; when set, every DDL statement the reconciler issues against the live database carries `ON CLUSTER <name>` through a template parameter and runs with the same `distributed_ddl_output_mode = 'throw_only_active'` as above, because the default mode throws `TIMEOUT_EXCEEDED` after `distributed_ddl_task_timeout` while a host is down even though the task stays queued for it; the DDL worker publishes the active markers that mode reads for `ON CLUSTER` tasks only since ClickHouse 24.11, so the `cluster` field requires that release where the rest of the design requires the floor of §8. The lock statements of §5.5 never carry the clause, because ClickHouse rejects a mutation with `ON CLUSTER` on a `KeeperMap` table. The catalogs are read through `clusterAllReplicas(<name>, system.tables)` and its siblings, always with `skip_unavailable_shards = 1`, since the default fails the whole read when one host is down, so that a replica-local property, a setting or a view query, that drifted on a replica other than the connected one still produces a statement. `clusterAllReplicas` connects to the other hosts with the credentials in `remote_servers`, or as the initiating user when the cluster defines a `cluster_secret`, and the documentation says so, because a cluster with neither connects as the `default` user with no password and fails the catalog read wherever that user is password-protected or disabled. The Jaeger user needs the `CLUSTER` grant for `ON CLUSTER` statements, which the shipped server configuration requires through `on_cluster_queries_require_cluster_grant`, and `REMOTE ON *.*` for `clusterAllReplicas`, under either fan-out mechanism. Setting `cluster` on a `Replicated` database is a configuration error that `plan` reports, as a rule of this design rather than of the server, so that one deployment never carries both fan-out mechanisms.

The design assumes the single-shard layout the backend writes to today. Every `ALTER` the reconciler issues runs with `alter_sync = 1` set explicitly, because ClickHouse Cloud ships `0` as its default on several releases, and the second `plan` below is what certifies the replicas, since under either fan-out mechanism the DDL worker executes an `ALTER` on a `Replicated*` table on one replica per shard and the others apply the replication-log entry afterwards, so the statement can return before the replica Jaeger is connected to carries the column: `alter_sync = 2` would wait on the others with no bound for an active replica and would make a down one throw `UNFINISHED` after `replication_wait_for_inactive_replica_timeout`, which inside `ON CLUSTER` the DDL worker treats as retriable and re-executes up to three times. A down replica applies the log entry when it returns, and no insert is routed to it meanwhile; it does accept connections again before its replication queue reaches the entry, which sits behind the fetches queued during the outage, and an insert routed to it in that window fails with `NO_SUCH_COLUMN_IN_TABLE`. That window is the backlog of the outage and is the one gap in the down-replica tolerance; a fleet that cannot accept it runs `clickhouse-schema apply` as the pre-upgrade job of §5.8 while every replica is up, which verifies all of them. One wait remains and is inherent: a `Replicated*` table executes its alters in order, so an additive statement that arrives while a type-change mutation of §5.4 is running on the table waits for that mutation to finish, which is hours for `spans`. The runbook for such a change therefore runs `clickhouse-schema apply` first, so that no additive statement is pending when the mutation starts, and states that a pod which restarts with a pending additive statement during the mutation waits for it. After the additive statements, and before the backend serves traffic, `plan` runs again through `clusterAllReplicas`, over `cluster` when it is set and otherwise over the cluster a `Replicated` database registers under its own name, which is why the `REMOTE` grant of the second bullet applies to both mechanisms, and is repeated with backoff for up to a minute while an additive statement is still outstanding on a replica that answered, because the replicas apply the log entry asynchronously; an additive statement still outstanding when the minute is up fails startup under `create_schema: true`, because a replica that still lacks a column would fail the first insert routed to it, and the next start plans again. A replica that is down is neither certified nor fatal, and deferred differences in that second plan are logged, not fatal. A multi-replica deployment with neither mechanism is documented as unsupported for `create_schema: true`, for the reason above.

### 5.7 Release snapshots and migration files

The diff engine also runs offline, against two sets of rendered templates rather than a live database, by creating both as scratch tables in a CI ClickHouse. A `make clickhouse-schema-snapshot` target writes `internal/storage/v2/clickhouse/sql/snapshots/<release>.sql`, the rendered schema with default parameters, and `migrations/<previous>_to_<release>.sql`, the plan from the previous snapshot to the new one, with refusals as comments naming the runbook. Both are committed by the release PR. They are documentation and audit trail, rendered with default parameters and therefore not executable against a deployment with its own `ttl`, `table_engine` or `cluster`: the binary never reads them, each file says so in its header, and the statements an operator runs come from `clickhouse-schema plan`, which renders with the deployment's configuration.

### 5.8 Operator path

```
jaeger ... --config config.yaml clickhouse-schema plan      # the plan against the live database, apply nothing
jaeger ... --config config.yaml clickhouse-schema apply     # apply the whole plan, additive and deferred, once
jaeger ... --config config.yaml clickhouse-schema render    # the rendered desired schema
```

`plan` prints the plan, exits non-zero when it is non-empty so it serves as a CI check, and prints refusals with the statements an operator would run. It needs `CREATE TABLE` and `DROP TABLE` on the configured database for its scratch tables, `SELECT ON system.data_skipping_indices`, which the server's implicit system grants omit under the shipped `select_from_system_db_requires_grant`, `REMOTE ON *.*` on a multi-replica cluster and `CLUSTER` besides when `cluster` is set (§5.6), and `table_engine` only to render the `CREATE` of a missing table; without the setting, the comparison of existing objects runs in full, the replication-mode row is skipped, and a missing table is a refusal naming the setting, which is the normal operator-managed configuration today and is tested as such (§5.9). `apply` is the one-shot procedure of §5.5, and needs `ALTER` on the database's tables and `ALTER VIEW MODIFY QUERY` on its views besides: it takes the lock where the server offers one, applies additive and deferred statements in template order, verifies, prints the refusals it cannot resolve, and exits non-zero when any remain. `render` needs `table_engine` and says so when it is absent, because a rendered schema without engines is not one. It is also the form for fleets that want the schema settled before pods roll, as one job that runs before the rollout, such as a Helm pre-upgrade hook, and not as a per-pod init container, which a rolling deployment runs once per pod and so concurrently across two releases. All three commands render with the configuration file's `ttl`, `table_engine` and `cluster`, so the output matches the deployment rather than a default. The root `jaeger` command is the collector's, which registers `--config` as a local flag that Cobra does not pass down, so the subcommand declares the same `--config` flag and feeds it to the same configuration loader.

### 5.9 Tests

All against the live ClickHouse that the integration suite already starts.

1. **Fresh install.** Startup on an empty database, then `plan` is empty, and every compared property (§5.2) of every object equals the rendered template as the server normalizes it.
2. **Upgrade from every release.** For each snapshot in `snapshots/`, apply it to an empty database, write the integration corpus through that release's writer, start, then run `clickhouse-schema apply`, and require the compared properties to equal a fresh install's, the plan to be empty afterwards, and the corpus to read back through the current reader, because catalog parity alone does not show that rows written before the upgrade are still valid under the new defaults and view queries. A template edit that needs a runbook fails this test with a refusal until the runbook exists and the test lists the change as expected.
3. **Idempotence and concurrency.** Start twice; start from two connections at once; the plan is empty after each. Start two binaries whose templates define a new column with different codecs at once and require the column to exist with one of the two codecs and the other to appear as a deferred difference in the next `plan`. Repeat for an index definition and a view query, and for a type, where the next `plan` is a refusal. Start two binaries against an empty database where one defines an extra column and a view that selects it, and require both columns and the view present after both have started. Against a two-replica table, run concurrent `ADD COLUMN IF NOT EXISTS` through both replicas and require both starts to succeed through the retry on error 517.
4. **Refusals.** For each refused row of the §5.2 table, create an object that differs from the template in that one way and require `plan` to return the refusal and exit non-zero, startup under `create_schema: true` to log it and start, and the writer to insert successfully afterwards where the difference is a widened type. Include a local table under `table_engine.replicated` and a replicated table under `merge_tree`, and `plan` under the default `create_schema: false` configuration with no `table_engine` against a database missing one table, which yields the refusal naming the setting while every other comparison runs.
5. **Deferred statements.** Each deferred row of the §5.2 table, including a codec removed from the template and a default removed from it: startup leaves the difference in place and logs it; `clickhouse-schema apply` resolves it; `apply_deferred_changes: true` resolves it at startup. Under `create_schema: false` startup issues no DDL at all, which the test asserts from `system.query_log`.
6. **Diff engine unit tests** on synthetic catalog rows: every row of the §5.2 table, the ignored list, `Nested` flattening, column placement, cross-object ordering, TTL clause extraction, prefix and qualifier stripping, and `formatQuerySingleLine` normalization of each view template.
7. **Lock and replication.** Against a ClickHouse started with its embedded Keeper, which a single server supports: two `clickhouse-schema apply` runs at once leave one waiting, an expired lease is taken over exactly once, a renewal racing a takeover loses, a release racing a successor leaves the successor's row, and `KeeperMap` absent runs unlocked with a notice. A two-replica Compose job covers convergence through `ON CLUSTER` and through a `Replicated` database, `cluster` set on a `Replicated` database being reported, a replica that is down during startup, which must leave the start successful and the replica carrying the column once it returns, and the verification failing startup when a replica that answered still lacks a column.

Run once with `merge_tree` and `ttl: 0` and once with `ttl` set, so the TTL clause is covered live, and against both the minimum ClickHouse version of §8 and the latest release, because the catalog columns the diff reads are what a server version can change. The CI ClickHouse already runs an embedded Keeper through `docker-compose/clickhouse/keeper.yaml`; test 7 adds `keeper_map_path_prefix` to that configuration, and the Compose job runs in the storage integration workflow with the other backends.

## 6. Upgrading an Existing Deployment

An existing deployment has the twelve objects as the previous release created them. On the first start of a binary with this mechanism:

- With `create_schema: true`, `plan` finds the ten OTLP columns missing from `spans`, all additive, and startup adds them. No operator action, which is the point of putting the mechanism behind the existing flag. Where `ttl` is set, the same plan also reports a deferred `MODIFY TTL` on `spans` and `trace_id_timestamps`, because the `toDateTime(...)` wrapper of §8 changes the TTL expression the templates render; startup logs it and `clickhouse-schema apply` resolves it.
- With `create_schema: false`, startup does nothing, exactly as today, and the writer fails on insert until the operator applies the columns; the operator now gets the ten statements from `clickhouse-schema plan`, which the release notes name, instead of deriving them from a diff of the templates.

A mismatch between the configuration and what was created a year ago is detected, which is new: today it is invisible. A `ttl` that was since changed becomes a deferred `MODIFY TTL` without materialization, logged at startup and applied by `clickhouse-schema apply`, after which the configured retention takes effect as parts merge. A table whose engine disagrees with the configuration, say a local `MergeTree` under a configuration that now says `replicated`, is a refusal logged at every start until the operator either rebuilds the table or corrects the configuration. A setting an operator tuned by hand, `index_granularity` among them, is a refusal logged at every start as well, and a customized codec or TTL is a deferred difference reported at every start, until the customization is carried into the template or accepted as a standing warning. Those warnings and a multi-replica cluster without fan-out (§5.6) are the ways the upgrade can be noisier than before; the first group is noisy about real differences, the second about a real problem. Grants are the way it can fail outright: a `create_schema: true` deployment whose Jaeger user holds only the `CREATE TABLE` that today's startup needs fails to start, because the plan needs `DROP TABLE` and `SELECT ON system.data_skipping_indices` (§5.8), the additive statements need `ALTER`, a multi-replica cluster needs `REMOTE`, and a self-hosted `Replicated` database with a password on `default` needs a `collection_name` with cluster credentials (§5.6), so the release notes list these ahead of the upgrade and the startup error names the missing one.

## 8. Open Questions

- **Minimum ClickHouse version.** `MODIFY QUERY` left its experimental setting in 23.11 and `keeper_map_strict_mode` arrived in 23.4. The backend has stated no floor so far; 24.3 is proposed and would be documented with M1. One fact bears on it: the TTL clauses the templates render today, `start_time + INTERVAL n SECOND` over a `DateTime64(9)` column on `spans` and `end + INTERVAL n SECOND` over a `SimpleAggregateFunction(max, DateTime64(9))` column on `trace_id_timestamps`, are rejected with `BAD_TTL_EXPRESSION` on 24.8 and 25.3 and accepted on 25.12, so either the floor is 25.12 or both templates wrap the column in `toDateTime(...)`. The template fix is proposed, as its own change before M1, because it widens compatibility and is a deferred TTL difference for existing databases rather than a rewrite.
- **`apply_deferred_changes` as a setting.** It exists so that a single-node installation keeps today's hands-off behavior for every change. The alternative is to have no such setting and ask even single-node operators to run `clickhouse-schema apply` for deferred changes, which is simpler and one more step.
- **A validate-only startup mode.** A migration runner embedded in a server binary conventionally offers three modes: apply at startup, validate at startup and fail or warn when the schema is behind, and do nothing. This design has the first and the third, through `create_schema`, and the validating form is `clickhouse-schema plan` run as an init container or a CI step, because a plan computed inside the collector under `create_schema: false` would need the scratch-table grants that the operator-managed configuration exists to withhold. A third `create_schema` value that plans at startup and only logs is proposed to wait for an operator who asks for it, since adding it later costs nothing and §5.3 is simpler with two rows than three.
