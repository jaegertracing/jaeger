## Abstract

The ClickHouse backend creates its twelve tables and materialized views at startup. It uses one `CREATE ... IF NOT EXISTS` template per object but cannot change an existing object. The missing OTLP span columns in #9789 are the first schema change since users received the schema. That change therefore has to establish how the schema is amended from now on.

This RFC describes the current mechanism and the requirements for its replacement. It analyses five families of approach. The first uses a migration framework to apply versioned delta files, as #9789 sketches and #9796 implements with golang-migrate. The second applies the same deltas through a small in-house migrator over a frozen baseline. The third keeps a full schema copy per version, as the Cassandra backend does. The fourth keeps today's templates as the living schema for fresh installs and applies short per-object deltas to existing databases, either written by the contributor or generated by a diff tool as Atlas and Prisma do. The fifth uses reconciliation: the backend compares the live catalog with the templates at startup and computes the `ALTER` statements itself, in the manner of Kubernetes controllers and Terraform.

This RFC recommends the fourth family in its hand-authored form. The twelve templates remain the readable source of truth and are edited in place. A PR that changes a template also adds one short delta file per changed object to the directory of the current schema version. A CI test proves that the previous version's schema plus the deltas equals the current templates, so the deltas are checked against the templates the way generated code is checked against its source. A small runner over the existing native connection records applied versions in a ledger table and applies pending deltas.

At startup, the runner applies only the additive statements of a pending version: new objects, columns and indexes. These statements are idempotent and commute across concurrent instances and releases. It logs every other statement, which changes a codec, default, setting, TTL or view query, and a one-shot operator command applies those. Startup can also apply them under an opt-in for deployments that ensure by construction that only one instance migrates. Changes that rewrite data never appear in a delta. They ship as operator runbooks, which the same CI test applies to prove that the runbook and the templates agree.

A delta changes only the property it names. An index, column, codec or setting that an operator added by hand therefore survives every upgrade that does not name it. The ledger records which versions ran. It does not certify runtime compatibility, and a newer recorded version never prevents an older binary from starting, so the previous release can restart during a rollback.

## 1. Motivation

Three conditions require a decision now.

1. **A schema change is pending.** #9789 adds ten columns to the `spans` table. Against an existing deployment, the startup statements are no-ops, so without a migration mechanism the columns never appear, and the writer fails on its first insert after the upgrade.
2. **RFC 0017 queues more.** Each codec, table setting and skip index adopted by RFC 0017 requires a metadata-only `ALTER TABLE`. Its `LowCardinality` wrappers change column types, which rewrites data and needs an operator procedure (§2.3). The backend will change its schema several times over the next few releases. Each change needs a defined path.
3. **Two PRs already implement one answer.** #9796 and #9799 adopt golang-migrate along the lines sketched in #9789. They place the entire baseline schema in a single `000001_initial_schema.up.sql`. Review of those PRs showed that the file layout, the test design and the library's fit need deciding before the code, which is what an RFC is for.

The Cassandra backend illustrates two problems to avoid. Its schema lives in `v001.cql.tmpl` through `v004.cql.tmpl` under [`internal/storage/v1/cassandra/schema/`](../../internal/storage/v1/cassandra/schema/), each a complete copy of every table. Upgrades are operator-run shell scripts in a `migration/` directory that the binary knows nothing about. Changing one table requires a new copy of the entire schema, and nothing records the version of a running keyspace. The ClickHouse mechanism has to improve on both properties.

## 2. Current State

### 2.1 Files

The schema has twelve files under [`internal/storage/v2/clickhouse/sql/`](../../internal/storage/v2/clickhouse/sql/), one per object. The `queries.go` file embeds each as a string variable:

| File | Object | Templated |
| --- | --- | --- |
| `create_spans_table.sql` | `spans` table | yes |
| `create_services_table.sql` | `services` table | yes |
| `create_services_mv.sql` | `services_mv` view | no |
| `create_operations_table.sql` | `operations` table | yes |
| `create_operations_mv.sql` | `operations_mv` view | no |
| `create_trace_id_timestamps_table.sql` | `trace_id_timestamps` table | yes |
| `create_trace_id_timestamps_mv.sql` | `trace_id_timestamps_mv` view | no |
| `create_attribute_metadata_table.sql` | `attribute_metadata` table | yes |
| `create_attribute_metadata_mv.sql` | `attribute_metadata_mv` view | no |
| `create_event_attribute_metadata_mv.sql` | `event_attribute_metadata_mv` view | no |
| `create_link_attribute_metadata_mv.sql` | `link_attribute_metadata_mv` view | no |
| `create_dependencies_table.sql` | `dependencies` table | yes |

The six table files are `text/template` documents, which `factory.go` renders with the `schemaTemplateParams` type:

```go
type schemaTemplateParams struct {
    TTLSeconds           int64  // zero renders no TTL clause
    MergeTree            string // ENGINE clause body for raw-row tables
    AggregatingMergeTree string // ENGINE clause body for derived tables
}
```

The `TTLSeconds` field comes from the `ttl` setting and renders `TTL start_time + INTERVAL n SECOND DELETE` on `spans` and `TTL end + ...` on `trace_id_timestamps`. The two engine strings come from the `table_engine` block that #9813 introduced: `merge_tree: {}` renders `MergeTree` and `AggregatingMergeTree`, and `replicated: {...}` renders `ReplicatedMergeTree('/path', 'replica')` and its aggregating counterpart. The materialized views use plain SQL because each writes `TO` its target table and has no engine of its own.

### 2.2 Startup behavior

The `newSchemaBuilder` function holds the twelve statements in dependency order, with tables before the views that read them. It renders the six templates. With `create_schema: true`, the `NewFactory` function executes the statements one by one over the native connection before the backend serves traffic. With `create_schema: false`, nothing runs, and the operator owns the tables.

The backend records nothing about the statements it executes. It has no version table or DDL fingerprint, and startup does not check whether the tables match the binary's expectations. A mismatch causes an insert or query error on the first request that touches the missing column.

### 2.3 What ClickHouse allows after `CREATE`

The parts of a table that can change in place determine the shape of a migration mechanism.

| Change | Statement | Cost | Replicated tables |
| --- | --- | --- | --- |
| Add a column | `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` | metadata only¹ | propagates through Keeper |
| Add a skip index | `ALTER TABLE ... ADD INDEX IF NOT EXISTS` | metadata only; existing parts are indexed on merge or by `MATERIALIZE INDEX` | propagates |
| Change a column's codec | `ALTER TABLE ... MODIFY COLUMN ... CODEC(...)` | metadata only; parts are re-encoded on merge | propagates |
| Replace a skip index | `DROP INDEX` then `ADD INDEX` | `DROP INDEX` is a mutation that only deletes index files; the new index is built on merge or by `MATERIALIZE INDEX` | propagates |
| Change a column's type, including adding `LowCardinality` | `ALTER TABLE ... MODIFY COLUMN ... <type>` | a mutation that rewrites every part² | propagates |
| Change a table setting | `ALTER TABLE ... MODIFY SETTING` | metadata only | replica-local³ |
| Change or remove TTL | `ALTER TABLE ... MODIFY TTL`, `ALTER TABLE ... REMOVE TTL` | a mutation by default; metadata only with `materialize_ttl_after_modify = 0`, after which the new expression applies as parts merge⁴ | propagates |
| Change a view's query | `ALTER TABLE <view> MODIFY QUERY` | metadata only; generally available since ClickHouse 23.11 | replica-local³ |
| Extend the sorting key | `ALTER TABLE ... MODIFY ORDER BY` | metadata only, and only by appending columns added in the same statement | propagates |
| Drop a column | `ALTER TABLE ... DROP COLUMN` | destroys data | propagates |
| Change `ENGINE`, `PARTITION BY`, or the existing sorting key | not possible | requires a new table and a copy | n/a |

- ¹ ClickHouse adds the column to each part's metadata. Existing parts have no value for it and evaluate the current default at read time until they merge. A later default change therefore changes the values read from those parts (§5.4).
- ² A mutation performs background work over every affected part. For a large `spans` table, this takes hours of I/O. Type changes therefore belong in operator runbooks, rather than startup steps (§5.4).
- ³ A `MODIFY SETTING` on a `Replicated*` table changes only the replica that receives it. The server code establishes this behavior: the `StorageReplicatedMergeTree::alter` method does not replicate an alter that changes only settings. The ClickHouse documentation does not state this restriction. A materialized view uses the `MaterializedView` engine, rather than a `Replicated*` engine, so its `MODIFY QUERY` is also local. Reaching every replica requires the fan-out described in §2.4.
- ⁴ With materialization off, an existing part keeps its rows and the TTL bounds recorded under the old expression until a merge rewrites it. A shortened TTL therefore reclaims a part that no longer merges only after an operator runs `ALTER TABLE ... MATERIALIZE TTL`. A `spans` partition that no longer receives inserts is such a part.

Replication does not cover all DDL. A column, index or codec `ALTER` on a `Replicated*` table is recorded in Keeper and applied on every replica. One connection therefore reaches the entire shard for these changes. In contrast, `CREATE TABLE`, `MODIFY SETTING` and a view's `MODIFY QUERY` affect only the server that the client reaches. Reaching the other servers requires `ON CLUSTER`, a database with the `Replicated` database engine, or a connection to each server. Section 5.6 applies this distinction to the design.

### 2.4 Facilities ClickHouse offers a schema tool

- **System catalogs.** The `system.tables` catalog provides `engine_full`, `sorting_key`, `partition_key`, `create_table_query` and, for views, `as_select`. The `system.columns` catalog provides each column's `type`, `default_kind`, `default_expression`, `compression_codec` and `position`. The `system.data_skipping_indices` catalog provides each index's `type_full`, `expr` and `granularity`. The `create_table_query` column is the server's own normalized rendering of the whole object: columns in order, defaults, codecs, indexes, engine, keys, TTL and settings for a table, and the `SELECT` for a view. Two objects created on one server from equivalent DDL therefore print the same text, which makes equality of two schemas a string comparison without a SQL parser.
- **A cross-process lock.** ClickHouse has no advisory locks. However, an `INSERT` into a `KeeperMap` table fails when the key exists if the query sets `keeper_map_strict_mode = 1`. This provides a compare-and-set operation with Keeper as the arbiter. It requires ClickHouse 23.4 or later, when `keeper_map_strict_mode` became available, and a Keeper ensemble. It also requires the opt-in `keeper_map_path_prefix` server setting, which no default configuration sets. Without that setting, the server refuses to create the table with `BAD_ARGUMENTS`. A strict-mode failure has no distinct error code: it returns `KEEPER_EXCEPTION` (error 999) with a "Node exists" message. The lock has to match that error and message.
- **DDL fan-out.** The `Replicated` database engine replays every DDL statement issued to one replica on all replicas. ClickHouse Cloud's `Shared` database engine builds on it and does the same for every database there. On a self-hosted cluster with an ordinary `Atomic` database, `ON CLUSTER <name>` provides the same fan-out per statement.

### 2.5 How the other backends do it

Section 1 covers Cassandra. Elasticsearch and OpenSearch have no comparable problem. The binary installs their mapping as an index template at startup. Indices roll by day or by alias rollover, so a new mapping applies to the next index without altering the previous one. Badger and memory have no persistent schema.

## 3. Requirements

This RFC judges the mechanism against the following criteria, which also form the comparison rows in §4.6.

1. **Per-object deltas.** Changing one column of one table changes one short file. It never requires a schema copy.
2. **One source of truth.** A fresh install and an upgraded install derive their final schema from one set of files. A second description, if one exists, is checked against the first by CI rather than by contributor discipline, the way generated code is checked against its source.
3. **Template parameters survive.** The `ttl` and `table_engine` settings describe the deployment, rather than the schema. Every `CREATE` has to render them. A migration file that hard-codes `MergeTree` can silently give a replicated deployment local tables, which is a data-loss configuration.
4. **The database's state is knowable.** The binary and the operator can identify which Jaeger schema changes a database has received and which are pending.
5. **Safe with concurrent instances.** Several Jaeger instances start together against one database. The result has to be correct regardless of which instance finishes second.
6. **Operator-managed schema stays possible.** With `create_schema: false`, the operator applies DDL by hand. The binary gives the operator exactly the DDL to apply, rendered for that deployment.
7. **Readable current schema.** A developer changing the writer can read a file to see the current `spans` table. The developer does not have to replay its history.
8. **Small dependency footprint.** The backend adds no database drivers or connection paths that it does not otherwise use.
9. **Little bookkeeping imposed on contributors.** Each version number, ordering rule, frozen file and generated golden file adds something for a contributor to learn and a reviewer to check.
10. **What runs in production is reviewable.** A schema PR reviewer can see the statements that will execute. An operator can see them before an upgrade.
11. **Operator customizations survive.** An upgrade changes only what Jaeger's schema change names. It does not undo an index, column, codec or setting that an operator added by hand to anything else.
12. **Planning writes nothing.** Computing what the database lacks changes no live object and needs no privilege beyond reads.

## 4. Approaches

### 4.1 Versioned deltas applied by a migration framework

Flyway, Liquibase, golang-migrate and goose use a numbered sequence of forward-only files. A table records which files have run, and a library applies pending files in order. This is the model sketched in #9789. The files together define the current schema: the baseline is version 1, and each change adds a file. #9796 implements this model with golang-migrate.

Two properties of golang-migrate affect this choice. First, the library does not constrain the layout. It reads each version as one `io.Reader` from any `fs.FS`, so the backend can render per-object files and concatenate them in memory. The single baseline file in #9796 is therefore a choice. Second, the ClickHouse driver fits this backend poorly. It requires a second connection through `database/sql`. Its process-local lock leaves concurrent instances dependent on idempotence alone. Its version-table handling and refusal to start against a newer recorded version each contradict a requirement in §3. The review of #9796 holds the specific objections. After workarounds for these problems, the library provides only the version table and the ordered walk, about a hundred lines of code.

### 4.2 Versioned deltas applied by an in-house migrator

An in-house migrator uses the same layout: a frozen baseline as version 1 and one directory per later version, with one file per object changed by that version. The backend implements the walk and version table over its native connection. This removes the driver problems above. The baseline, however, no longer describes the readable current schema. Contributors read a golden `SHOW CREATE TABLE` dump instead, and the templates of §2.1 stop being the schema and become one historical version of it.

### 4.3 Full copy of the schema per version

Cassandra uses a complete, readable schema for each version. The difference between two versions is whatever a human writes into a migration script. This model necessarily fails requirement 1 and records nothing in the database. It appears here because it is the repository's precedent.

### 4.4 Living templates for fresh installs, deltas for upgrades

This approach keeps today's templates as the readable current schema and edits them in place. A fresh install creates the tables from the templates. An existing database receives short delta files, one per changed object, that the PR commits alongside its template edit. A ledger table records which versions a database has received.

The deltas can come from two sources.

- **4.4a, hand-authored deltas.** The contributor writes the delta alongside the template edit. The two describe the same change twice, so a CI test creates one database from the previous version's schema plus the deltas and another from the current templates, and requires the server's `create_table_query` text of every object to be equal (§5.7). The test needs no vocabulary of properties, because equality of two objects created on the same server is a string comparison (§2.4). This is the check that makes the templates the single source of truth: a delta that does not reproduce them cannot merge, just as stale generated code cannot.
- **4.4b, generated deltas.** Atlas calls this the versioned workflow with `atlas migrate diff`; Prisma and Alembic use it too. A tool compares the templates with the previous version's schema and writes the delta. The contributor reviews and commits it. Generation needs a per-property diff engine that turns each difference into a statement, which is the same engine that reconciliation (§4.5) runs in production, moved to a developer's machine. Its output is also the first draft of a reviewed delta, so the two variants differ in tooling and not in what reaches production.

Both variants apply only additive deltas at startup and leave the rest to an operator command, which §5 specifies. Both keep the version record, so the state of a database is the list of versions it has received. The version directory is opened once per release cycle rather than once per PR, so concurrent PRs add files to the same directory without a numbering conflict (§5.1). The ledger records a checksum per file, so a fleet deployed from trunk that received an earlier shape of the open version runs the changed file again; the file's additive statements are idempotent, so the repetition is safe.

A fresh install has to run the deltas too, with every statement a no-op against tables the templates just created. The shortcut of recording the newest version without running them is unsafe: two releases starting against an empty database both find the tables missing, the newer one's `CREATE IF NOT EXISTS` loses to the older one's, and the newer binary would then record a version whose column the table lacks.

### 4.5 Reconciliation

Reconciliation describes the desired schema once, declaratively. The tool computes the statements needed to bring the live database to that state. Kubernetes controllers use this model for resources, Terraform uses it for infrastructure, and Atlas, Skeema, sqldef and Prisma use it for relational schemas. For ClickHouse, Atlas's ClickHouse driver, PostHog's `chschema`, Noibu's `housekeeper` and the Python `clickhouse-migrations` tool's `diff` command use this model. These tools run from a CLI at deploy time.

Reconcilers also have an established form that runs inside an application at startup, under the constraint that it only ever adds. Ent's `Schema.Create` method and GORM's `AutoMigrate` method inspect the live database and issue `CREATE TABLE`, `ADD COLUMN` and `ADD INDEX` for objects present in the Go schema but absent from the database. Neither drops a column or index unless the caller passes an explicit option, because a reconciler that converges exactly would read a rename as a drop plus an add.

For this backend, the twelve templates would describe the desired schema. At startup, the backend would render them, create each table under a throwaway name in the same database, read the scratch and live objects from the system catalogs, and compare them per property. Scratch tables are needed because a session-scoped `CREATE TEMPORARY TABLE` reports empty keys, a bare engine and no indexes in the catalogs on ClickHouse 25.12. The diff would apply the additive statements of §2.3 at startup, report the metadata-only non-additive ones for an operator command, and refuse the rest. Anything present in the live table but absent from the templates would be left alone.

This approach detects drift and gives an operator the exact statements their database lacks. It has three costs that the other approaches do not share. The scratch tables make planning a write: every start creates and drops twelve tables, needs `CREATE TABLE` and `DROP TABLE` grants, adds twelve entries to a `Replicated` database's DDL log, and needs a sweep for scratch tables that a crashed run left behind. The comparison needs a vocabulary of every property it compares, with a fixed action per property, because a live difference has no label: an operator's customization, a partially completed upgrade and a schema created by the previous release all look alike in the catalog. And an `apply` resets every customized codec, setting, default and TTL to the template on every run, so an operator who customizes one property cannot receive Jaeger's own deferred changes without losing it.

### 4.6 Comparison

| Criterion (§3) | 4.1 golang-migrate deltas | 4.2 in-house deltas | 4.3 full copies | **4.4a templates + authored deltas** | 4.4b templates + generated deltas | 4.5 reconciliation |
| --- | --- | --- | --- | --- | --- | --- |
| 1. Per-object deltas | 🟢¹ | 🟢 | ❌ | 🟢 | 🟢 | 🟢 |
| 2. One source of truth | 🟢 | 🟢 | ❌² | 🟢³ | 🟢³ | 🟢 |
| 3. Template parameters survive | 🟢⁴ | 🟢 | 🟢 | 🟢 | 🟢 | 🟢 |
| 4. Database state knowable | 🟢⁵ | 🟢⁵ | ❌ | 🟢⁵ | 🟢⁵ | 🟢⁶ |
| 5. Safe with concurrent instances | ❌⁷ | 🟨⁸ | n/a | 🟢⁹ | 🟢⁹ | 🟢⁹ |
| 6. Operator-managed schema | 🟨¹⁰ | 🟢¹¹ | 🟢 | 🟢¹¹ | 🟢¹¹ | 🟢¹² |
| 7. Readable current schema | 🟨¹³ | 🟨¹³ | 🟢 | 🟢 | 🟢 | 🟢 |
| 8. Dependency footprint | 🟨¹⁴ | 🟢 | 🟢 | 🟢 | 🟢 | 🟢 |
| 9. Little bookkeeping | ❌¹⁵ | ❌¹⁵ | 🟨 | 🟢¹⁶ | 🟢¹⁶ | 🟢¹⁶ |
| 10. Production statements reviewable | 🟢 | 🟢 | 🟨 | 🟢 | 🟢 | 🟨¹⁷ |
| 11. Operator customizations survive | 🟢¹⁸ | 🟢¹⁸ | 🟨 | 🟢¹⁸ | 🟢¹⁸ | ❌¹⁹ |
| 12. Planning writes nothing | 🟢 | 🟢 | n/a | 🟢 | 🟢 | ❌²⁰ |
| Code to own²¹ | 🟨 ~150 lines of glue and driver workarounds | 🟨 ~200 lines: runner and ledger | 🟢 none | 🟢 ~250 lines: runner, ledger and the equality test | ❌ ~250 lines plus a 600 to 900 line generator | ❌ 1200 to 1600 lines: per-property diff, generator, scratch lifecycle, replica verification |

🟢 meets the criterion; 🟨 meets it with a caveat; ❌ fails it.

- ¹ The library reads each version as one stream, so the backend can concatenate per-object files in memory. The single baseline file in #9796 is that PR's choice, rather than a framework constraint.
- ² The full schema copy describes the resulting state, and the human-written migration script that takes a database from the previous copy to it describes the transition. They are two descriptions, and nothing checks them against each other.
- ³ The deltas are a second description of each change, checked against the templates by the equality test of §5.7 on every PR. The test fails when a delta is missing, wrong or stale, so the templates remain the only description a contributor has to get right.
- ⁴ As it stands, #9796 renders the baseline through the templates; the earlier shape that its review commented on hard-coded the engine.
- ⁵ The ledger states which versions the database received and which are pending, which is the question an upgrade asks. It does not reveal a change made outside Jaeger, and under requirement 11 the mechanism must not act on one.
- ⁶ The live catalog determines the plan, so the report also includes drift. The report cannot say whether a difference is a customization, a partial upgrade or the previous release's shape.
- ⁷ The library does not create its version table idempotently, so first starts race. Pending versions can also interleave across instances.
- ⁸ Correct if every statement is idempotent and no version reassigns a property assigned by an earlier version. The additive-only startup of footnote 9 would make it 🟢.
- ⁹ Startup applies only additive statements. They are idempotent and commute, so they need no coordination. Only a one-shot operator command runs non-additive statements (§5.5). The ledger is insert-only, so concurrent records union.
- ¹⁰ golang-migrate applies files as stored. The operator receives the files and the message "versions 2 and 3 are pending", and renders the parameters by hand.
- ¹¹ The `plan` command renders the pending versions' statements with the deployment's `ttl`, engine and cluster, followed by the ledger inserts that record them, so a hand-applied version is recorded (§5.8).
- ¹² The operator receives exactly the statements that the database lacks, computed against that database.
- ¹³ A generated golden dump provides the readable current schema, rather than the authored files.
- ¹⁴ The library's driver requires a second `database/sql` connection.
- ¹⁵ Contributors manage version numbers per PR, a frozen baseline and a golden dump, and follow a rule that released versions never change.
- ¹⁶ The contributor edits the template and, for 4.4a, writes the delta file in the open version's directory. Snapshots are produced by a `make` target when a version closes, and CI enforces the immutability of closed versions and the equality of deltas and templates (§5.7). Under 4.5 the same `make` target produces the release snapshots.
- ¹⁷ The PR shows the template edit rather than the `ALTER` statements. Only a release-time generated file and the printed plan show those statements.
- ¹⁸ A delta touches only the properties it names. A `MODIFY COLUMN ... CODEC` delta overwrites an operator's customization of that one column's codec once, and the PR that ships it can say so. A customization of anything the delta does not name survives.
- ¹⁹ Each `apply` resets every customized codec, setting, default or TTL to the template. An operator keeps a customization only by never running `apply`, which also forgoes Jaeger's own deferred changes, or by adding an accepted-differences list that reintroduces the classification of footnote 6.
- ²⁰ A plan creates and drops scratch tables in the configured database (§4.5). This requires `CREATE TABLE` and `DROP TABLE` there and a sweep for abandoned tables.
- ²¹ Estimates of production and CI code without tests. The equality test of 4.4a compares `create_table_query` strings and needs no property vocabulary. The generator of 4.4b and the diff of 4.5 are the same engine; 4.5 adds the scratch-table lifecycle, the multi-round convergence for concurrent releases and the replica verification that reads every compared property back.

This RFC recommends option 4.4a. Rows 10, 11 and 12 and the code-to-own row decide the choice. The statements that run in production are the statements a reviewer read in the PR. A delta changes only what it names, so an operator's customizations survive. Planning reads one ledger table. The production code is a runner and a ledger, and the CI check is a string comparison. Reconciliation wins only row 4's drift detection, which requirement 11 forbids the mechanism to act on, and which can arrive later as a diagnostic command without owning production upgrades. Option 4.4b differs from 4.4a only in tooling, so a generator can be added later if hand-written deltas prove error-prone, without changing the layout, the runner or the tests.

Several costs are shared by every option and therefore do not appear as differences in the matrix. Rolling deployments need the compatibility rules of §5.4 whether a version number or a diff drives the upgrade. Default changes can change the values read from old parts, and view changes can need a backfill, under every option. Replicated DDL needs the fan-out and the completion contract of §5.6 under every option. The additive-only startup is likewise available to every delta-based option, not only to reconciliation.

## 5. Design

### 5.1 Files

The twelve template files keep their locations and names. They remain the complete description of the current schema and change in place when the schema changes. The OTLP columns in #9789 add ten lines to `create_spans_table.sql`, and RFC 0017's codecs change that same file. The templates render with the `schemaTemplateParams` type as today.

Two directories join them under `internal/storage/v2/clickhouse/sql/`:

```
sql/
  create_spans_table.sql          # living templates, as today
  ...
  migrations/
    002/
      spans.sql                   # ALTERs that take spans from version 1 to version 2
      trace_id_timestamps.sql
    003/
      spans.sql
      runbooks/
        spans_low_cardinality.sql # data-rewriting change, never run by the binary
  snapshots/
    001.sql                       # rendered templates at the close of version 1
    002.sql
```

A schema version is an integer. Version 1 is the schema that the previous release creates, so it has no `migrations/` directory. A new directory opens once per release cycle: the first schema PR after a release creates `migrations/<N>/` and writes `snapshots/<N-1>.sql` with the `make clickhouse-schema-snapshot` target, which renders the templates at that PR's base with default parameters. Later PRs in the same cycle add or extend files in the open directory. Two PRs that change different objects therefore never conflict, and two that change the same object conflict in one file, where a reviewer wants to see it. CI rejects a change to any directory or snapshot older than the open version by comparing them with the last release tag.

A delta file is a `text/template` document like the table templates and renders with the same parameters. Statements are separated by a semicolon at the end of a line. A file holds the statements for one object in the order they execute. It never references the ledger, which the runner maintains. Each statement has to match one form in the vocabulary of §5.2, and a CI test rejects any that does not. A change that the vocabulary excludes, such as a type change, ships as a file under `runbooks/` in the same directory. The binary never executes a runbook. The equality test of §5.7 does, so the runbook is proven to reach the templates, and the PR's description and the release notes name it.

### 5.2 The runner

```go
// schemaMigrator applies the pending schema versions under sql/migrations to the
// live database and records them in the ledger table.
type schemaMigrator struct {
    conn   driver.Conn
    params schemaTemplateParams
}

// plan reads the ledger and returns every statement of every pending version,
// rendered for this deployment and classified, without executing anything.
func (m *schemaMigrator) plan(ctx context.Context) (schemaPlan, error)

// apply executes the statements of the given classes in version and file order
// and records each file in the ledger after its statements succeed.
func (m *schemaMigrator) apply(ctx context.Context, p schemaPlan, classes ...statementClass) error

type schemaPlan struct {
    Versions []pendingVersion
}

type pendingVersion struct {
    Version    int
    Files      []pendingFile
}

type pendingFile struct {
    Object     string
    Checksum   string          // of the file before rendering
    Statements []statement
}

type statement struct {
    Class statementClass // additive or deferred
    SQL   string         // rendered
}
```

#### The ledger

```sql
CREATE TABLE IF NOT EXISTS jaeger_schema_migrations (
    version        UInt32,
    object         LowCardinality(String),
    class          LowCardinality(String),  -- 'additive' or 'deferred'
    checksum       String,
    jaeger_version String,
    applied_at     DateTime DEFAULT now()
) ENGINE = {{ .MergeTree }}
ORDER BY (version, object, class, applied_at)
```

The ledger renders with the deployment's engine, so under `table_engine.replicated` it is a `Replicated*` table and its rows reach every replica. It is insert-only. A file is pending when the ledger holds no row for its version, object, class and current checksum. A file whose checksum changed since it was recorded is pending again, which happens only for the open version in a fleet deployed from trunk (§4.4). The ledger therefore records what ran and when, and nothing in it ever has to be updated or deleted. An older binary ignores rows for versions it does not know, because a newer recorded version says nothing about whether this binary can run (§5.3).

#### Statement vocabulary

The runner classifies each rendered statement by its leading keywords. The class determines who runs it.

| Form | Class | Notes |
| --- | --- | --- |
| `CREATE TABLE IF NOT EXISTS` | additive | a new table; renders the deployment's engine |
| `CREATE MATERIALIZED VIEW IF NOT EXISTS` | additive | a new view; carries no engine |
| `ALTER TABLE <t> ADD COLUMN IF NOT EXISTS` | additive | one column per statement; `AFTER` is allowed |
| `ALTER TABLE <t> ADD INDEX IF NOT EXISTS` | additive | |
| `ALTER TABLE <t> MODIFY COLUMN <c> CODEC(...)`, `... REMOVE CODEC` | deferred | takes no type, so it never rewrites data |
| `ALTER TABLE <t> MODIFY COLUMN <c> DEFAULT ...`, `... REMOVE DEFAULT` | deferred | subject to rule 4 of §5.4 |
| `ALTER TABLE <t> MODIFY SETTING` | deferred | replica-local (§2.3); read-only settings fail at apply time |
| `ALTER TABLE <t> MODIFY TTL ... SETTINGS materialize_ttl_after_modify = 0`, `... REMOVE TTL` | deferred | the setting is mandatory; without it the statement is a mutation and the CI test rejects it |
| `ALTER TABLE <t> DROP INDEX IF EXISTS` | deferred | always followed by the `ADD INDEX` that replaces it |
| `ALTER TABLE <v> MODIFY QUERY` | deferred | replica-local (§2.3) |
| `ALTER TABLE <t> MODIFY ORDER BY` | deferred | only appends columns added in the same version |
| anything else | rejected | type changes, drops, `MATERIALIZE`, engine or key changes belong in a runbook |

Additive statements are idempotent and commute: two such statements from different releases for the same object either agree or preserve the definition that ran first, and the definition that ran first is what the next version's delta expects, because rule 2 of §5.4 forbids a release from redefining a property added by an earlier one. Startup therefore applies them without coordination.

Deferred statements do not commute. If an older release's `MODIFY QUERY` on a view lands after a newer release's, the view computes derived rows with the wrong query until someone notices. An older TTL can expire parts in that interval. ClickHouse has no primitive that safely orders these statements across concurrent instances: a distributed DDL that outlives its lease keeps executing, a `Replicated` database retries remote DDL until completion, and a lock cannot revoke queued work. Startup therefore never applies deferred statements by default. It logs them with the command that applies them, and the one-shot operator command in §5.8 applies them from one place at a time. The opt-in `apply_deferred_changes: true` also allows startup to apply them. A deployment sets this only if it ensures by construction that a single instance migrates, as in a single-node installation. A per-pod init container does not ensure that: a rolling deployment runs old and new releases' init containers concurrently.

#### Startup steps with `create_schema: true`

1. The runner checks `system.tables` for the `spans` table and the ledger table before it creates anything. A database with `spans` and no ledger was created by the previous release, and the runner records version 1 for it after step 2. A database with neither is a fresh install.
2. It executes the twelve templates and the ledger's `CREATE TABLE IF NOT EXISTS`, as today.
3. It reads the ledger and computes the pending files. On a fresh install, every version is pending; its additive statements are no-ops against tables the templates just created, and the runner records them like any other version. Its deferred statements are also recorded as applied, because the templates already carry their result. The exception described in §5.5 is two releases sharing a fresh install.
4. It executes the pending additive statements in version order, and within a version in template order, with tables before the views that read them. It retries each statement on error 517 (§5.5). After a file's additive statements succeed, it inserts the file's `additive` ledger row. With `apply_deferred_changes: true` it does the same for the deferred statements and rows.
5. It verifies the additive statements on every replica (§5.6) and then lets the backend serve traffic. It logs the pending deferred statements and the pending runbooks, each with the command or document that applies it.

The runner needs no `table_engine` to render an `ALTER`. A missing `table_engine` matters only for a `CREATE` of a new table, which fails at render time with a message naming the setting.

### 5.3 Startup behavior

| `create_schema` | Pending | Behavior |
| --- | --- | --- |
| `true` | nothing | Start. |
| `true` | additive statements, possibly with deferred ones | Apply the additive statements, verify them (§5.6), record them, log the deferred statements with the operator command, and start. With `apply_deferred_changes: true`, apply and record the deferred ones too. |
| `true` | only deferred statements | Log them and start; with `apply_deferred_changes: true`, apply, verify, record, and start. |
| `true` | the ledger cannot be read or created | Fail: creating the schema was asked for and needs the privileges to record it. |
| `false` | not computed | Start, as today. Nothing is created, read or written at startup; `clickhouse-schema plan` computes the plan on demand, with whatever user has the privileges. |

Startup fails for exactly three reasons: the ledger cannot be read or created, an additive statement fails to apply, or the verification in §5.6 finds an additive statement still outstanding on a replica that answers. Failure to apply includes a Jaeger user without the `ALTER` grant. The last two failures mean that a column written by this binary is missing somewhere. That is the one difference that prevents the binary from working.

A pending deferred statement or runbook does not establish that the binary cannot run. A binary whose template specifies `String` can still write a column changed to `LowCardinality(String)` by a runbook. Likewise, the previous release restarted during a rollback finds ledger rows for a version it does not know and ignores them. Failing either start would make every upgrade a one-way door, so pending work is logged at every start and gates nothing.

### 5.4 Rules for changing the schema

1. **Expand only.** A template edit adds columns, indexes, codecs and settings or changes a view's query. It never removes or renames a column read or written by the previous release. A removal changes the template in the release after the one that stops using the column. Even then, no delta drops the column; a runbook does. During a rolling deploy, an older binary therefore always runs against a schema that is a superset of its expectations. The existing `INSERT` statements with explicit column lists and `SELECT` statements with explicit columns already tolerate that schema.
2. **No data-rewriting changes in a delta, and no redefinition across versions.** Runbooks change column types, sorting keys, partition keys and engines. Column type changes include `LowCardinality` and any change inside the nested attribute groups of `events` and `links`. A TTL change is deferred and runs without materialization (§2.3). A version never adds a column or index with a definition that differs from one an earlier version added, because concurrent releases would then race to define it. The equality test of §5.7 fails for a template edit that no delta or runbook reproduces, so the PR that changes the template ships one or the other. A runbook has to leave the previous release able to write the table, because that release restarts during a rollback. Widening a type to `LowCardinality` or `Nullable` meets this requirement; narrowing a type does not.
3. **A view change is forward-only and must leave old rows valid.** `MODIFY QUERY` and `CREATE` of a missing view affect only rows inserted afterwards. They repair no rows already in the target table. A view edit may therefore add derived columns, for which old rows hold defaults. It may also change the query if existing target rows remain correct under the new definition. A change to grouping, filtering or aggregation that makes old rows wrong requires more than a delta. It ships with a backfill runbook that repopulates the target from `spans`, and the PR states that requirement. Because `MODIFY QUERY` is deferred, successful startup does not enable a feature that depends on the changed view. The feature's release notes state that `clickhouse-schema apply` is the prerequisite. Never drop and recreate a view, because inserts during the gap would bypass it.
4. **Defaults are semantics, not metadata.** A new column takes its type default. An `INSERT` from a binary that does not know about the column therefore still succeeds. Changing an existing column's `DEFAULT` requires only metadata changes to execute, but it changes the data read. Parts written before the column existed hold no value for it and evaluate the current default. After a default change, a row in such a part reads the new default. A row in a part that materialized the column retains the old value. Thus, a row's value depends on its part's history. A default change is acceptable only if every such row is correct under the new default. Otherwise, it ships with a runbook that runs `ALTER TABLE ... MATERIALIZE COLUMN` before the change. The deferred `MODIFY COLUMN ... DEFAULT` executes the change; it does not certify its correctness.

### 5.5 Concurrency

Startup applies only additive statements (§5.2), each idempotent, in version and template order. Concurrent instances of one release produce the same schema. A duplicate `ADD COLUMN IF NOT EXISTS` normally does nothing. However, on a `Replicated*` table reached concurrently through two replicas, it can fail with `CANNOT_ASSIGN_ALTER` (error 517, "metadata on replica is not up to date"). The server's message states that the error can be retried. The losing statement did not execute. Although the replication log brings the winner's entry to the losing replica, the losing instance has to see its own statement applied before verification. The runner therefore retries every additive statement with backoff on that error for up to a minute. If retries expire, startup fails, and the next start applies again.

Concurrent instances of two releases produce the union of their additive statements, each defined once by rule 2 of §5.4. The ledger is insert-only, so both record what they ran and the rows union. One case remains: two releases that share a fresh install. Both find the tables missing, and the older one's `CREATE` wins. The newer one records every version's deferred statements as applied in step 3 of §5.2, although the table carries the older template's codec, default or view query for anything the open version changed. The window is one start against an empty database with two releases at once, which a first deployment does not do. For that case, `clickhouse-schema apply --from <version>` re-applies the deferred statements of that version onward and records them.

The same rules bound the work charged to a fleet. Every startup statement changes only metadata, and retries have a time limit. A readiness probe therefore sees seconds of schema work rather than a mutation. The exception is an additive statement that arrives while a runbook's mutation runs on the same table (§5.6). A fleet that wants no schema work in its pods runs `clickhouse-schema apply` as one pre-upgrade job (§5.8) and sets `create_schema: false` in the pods. This is also the least-privilege configuration, because the pods then need only `INSERT` and `SELECT`.

This RFC designs the operator command for deferred statements to run once, from one place. As a guard rail against two operators running it at once, the command takes a lock on a server that offers `KeeperMap` (§2.4). A `jaeger_schema_lock` table holds one row keyed by the database name. The value contains the holder's identity and a lease expiry. Every mutation uses `keeper_map_strict_mode = 1` and a predicate on the current value. Acquisition, renewal, takeover of an expired lease and release are therefore compare-and-set operations that fail instead of overwriting another value.

The lock row is created once and never deleted. Release uses the same conditional update to write an empty holder and an expired lease. A later acquisition takes the free row through that operation too. This is necessary because `KeeperMap` compares a row's Keeper version rather than its content. A deleted and recreated row starts again at version 0. A delete from a paused former holder would therefore remove a row just recreated by a later holder.

A mutation whose predicate matches no row succeeds without changing anything. The command therefore reads the row back after every mutation and holds the lease only while the row names its identity. If the read returns another holder, the mutation did not take effect, and the command stops. The lock serializes the command's own statements but cannot revoke distributed DDL queued by a previous holder. It is therefore a guard rail; the instruction to run the command once, from one place, provides the guarantee. If `KeeperMap` is unavailable, the command reports that fact and runs unlocked.

### 5.6 Replicated clusters

The runner executes against the replica that the connection reached. Column, index, codec and TTL `ALTER` statements on `Replicated*` tables propagate through Keeper. `CREATE`, `MODIFY SETTING` and a view's `MODIFY QUERY` affect only that replica (§2.3). A deployment with more than one replica therefore needs DDL fan-out.

The alternative would repair each replica when an instance next connects to it. That works only while the replica's Keeper metadata matches the current template. A template `CREATE` against metadata with a different column or codec fails with `INCOMPATIBLE_COLUMNS`. A different TTL or skip index causes `METADATA_MISMATCH`. Only a settings difference is accepted, because it is local to the replica. Repair through whichever instance connects next is therefore not reliable. ClickHouse offers two mutually exclusive fan-out mechanisms.

- **A `Replicated` database**, or the `Shared` database that ClickHouse Cloud assigns to every database, replays every DDL statement on every replica. The runner detects either engine through `system.databases.engine`. It issues DDL with `distributed_ddl_output_mode = 'throw_only_active'`, which waits for replicas that are up and reports a failure on any of them. In contrast, `throw` waits the full `distributed_ddl_task_timeout` for a down replica. Such a database rejects `ON CLUSTER` with any name except its own. Since ClickHouse 24.9, it also rejects `Replicated*` engines with explicit arguments by default, through `database_replicated_allow_replicated_engine_arguments`. This deployment therefore uses `table_engine.replicated` without `keeper_path`, `replica_name` or `cluster`; the database supplies the replication arguments. A `Replicated` database registers a cluster under its own name, and the verification of this section reads through that cluster; on ClickHouse Cloud the `default` cluster takes that role instead. The database's registered cluster connects with the credentials of the named collection in the database's `collection_name` setting, or as `default` with no password when there is none. A self-hosted `Replicated` database with a password on its `default` user therefore needs a collection with `cluster_username` and `cluster_password` before verification can read other replicas. #9813 made the `keeper_path` and `replica_name` fields optional so that the server's `default_replica_path` and `default_replica_name` apply when they are absent, which is the same rendering.
- **`ON CLUSTER`** provides fan-out for a self-hosted cluster with an ordinary `Atomic` database. The backend adds an optional `cluster` field to `table_engine.replicated`. When set, a template parameter adds `ON CLUSTER <name>` to every DDL statement that the runner issues, in the templates and the deltas alike. Those statements use the same `distributed_ddl_output_mode = 'throw_only_active'` as above, because the default mode throws `TIMEOUT_EXCEEDED` after `distributed_ddl_task_timeout` while a host is down, even though the task stays queued for it. For `ON CLUSTER` tasks, the DDL worker publishes the active markers used by `throw_only_active` on every release admitted by the floor in §8. The lock statements in §5.5 never carry this clause, because ClickHouse rejects a mutation with `ON CLUSTER` on a `KeeperMap` table. The runner reads catalogs through `clusterAllReplicas(<name>, system.columns)` and its siblings, always with `skip_unavailable_shards = 1`, since the default fails the entire read if one host is down. The `clusterAllReplicas` function connects to other hosts with the credentials in `remote_servers`, or as the initiating user if the cluster defines a `cluster_secret`. The backend's documentation has to say so, because a cluster with neither connects as the `default` user with no password and fails the catalog read wherever that user has a password or is disabled. The Jaeger user needs the `CLUSTER` grant for `ON CLUSTER` statements, as required by the shipped server's `on_cluster_queries_require_cluster_grant` setting. It also needs `REMOTE ON *.*` for `clusterAllReplicas` under either fan-out mechanism. This design treats `cluster` on a `Replicated` database as a configuration error reported at startup and by `plan`, even though the server does not impose that rule, so that one deployment never carries both fan-out mechanisms.

The design assumes the single-shard layout that the backend writes to today. The runner sets `alter_sync = 1` explicitly on every `ALTER`, because ClickHouse Cloud ships `0` as its default on several releases; the verification below is what certifies the replicas. Under either fan-out mechanism, the DDL worker executes an `ALTER` on a `Replicated*` table on one replica per shard. Other replicas apply the replication-log entry afterwards. The statement can therefore return before the replica connected to Jaeger has the column.

The other wait modes do not provide a suitable guarantee. With `alter_sync = 2`, an active replica can delay completion without a bound. In that mode the `ALTER` also throws `UNFINISHED` for a down replica after `replication_wait_for_inactive_replica_timeout`. Within `ON CLUSTER`, the DDL worker treats that error as retriable and re-executes the statement up to three times. The `alter_sync = 3` mode waits only for active replicas, but the settings catalogs of some supported releases do not describe it. The design therefore relies on neither mode.

A down replica applies the log entry when it returns. No insert is routed to it while it is down. However, it accepts connections before its replication queue reaches the entry, which follows the fetches queued during the outage. An insert routed there in that window fails with `NO_SUCH_COLUMN_IN_TABLE`. This window lasts for the outage backlog and is the one gap in tolerance of down replicas. A fleet that cannot accept the gap runs `clickhouse-schema apply` as the pre-upgrade job in §5.8 while every replica is up. That job verifies all replicas.

One wait is inherent in the design. A `Replicated*` table executes alters in order. An additive statement that arrives during a type-change mutation from a runbook on that table waits for the mutation to finish. For `spans`, this takes hours. The runbook therefore runs `clickhouse-schema apply` first, leaving no additive statement pending when the mutation starts. It also states that a pod restarted with a pending additive statement during the mutation waits for it.

After the additive statements and before the backend serves traffic, the runner verifies them. The fixed statement forms of §5.2 name the table and the column or index they add, so the runner extracts those names and reads `system.columns` and `system.data_skipping_indices` through `clusterAllReplicas`. It reads over `cluster` when that is set, and otherwise over the cluster that a `Replicated` database registers under its own name, or `default` on ClickHouse Cloud. This is why the `REMOTE` grant in the second bullet applies to both mechanisms. Replicas apply log entries asynchronously, so verification repeats with backoff for up to a minute while a column or index remains absent on a replica that answers. If it remains absent after that minute, startup with `create_schema: true` fails, because a replica that still lacks a column would fail the first insert routed to it. The next start applies again. A down replica is neither certified nor fatal.

This RFC declares a multi-replica deployment with neither fan-out mechanism unsupported for `create_schema: true`, for the reason above, and the backend's documentation has to say so.

### 5.7 Snapshots and the equality test

The `make clickhouse-schema-snapshot` target renders the templates with default parameters, `merge_tree` and `ttl: 0`, to `snapshots/<N>.sql`. The PR that opens version N+1 commits the snapshot of version N (§5.1). The binary never reads a snapshot, and each file's header states that the file is rendered for default parameters and is not executable against a deployment with its own `ttl`, `table_engine` or `cluster`. Operators obtain executable statements from `clickhouse-schema plan`.

The equality test runs on every PR against the live ClickHouse of the integration suite. For each snapshot N below the open version, it:

1. creates database A from `snapshots/<N>.sql` and applies every delta file of versions N+1 through the open version in order, both classes, followed by every runbook of those versions;
2. creates database B from the current templates with the same parameters;
3. reads `create_table_query` from `system.tables` for every object in both databases, replaces the database name, and requires the twelve strings to be equal;
4. writes the integration corpus into database A through the writer of version N, taken from the release that closed it, before step 1's deltas run, and reads it back with the current reader after they run. Catalog equality alone does not show that rows written before the upgrade remain valid under the new defaults and view queries.

The test runs once with `ttl: 0` and once with `ttl` set, so that a TTL delta is proven against the TTL clause the templates render. It runs against both the minimum ClickHouse version in §8 and the latest release, because the server's rendering of `create_table_query` is the comparison, and a server version can change it. A template edit without a matching delta or runbook fails step 3. A delta without a matching template edit fails it too. Step 3 is a string comparison, so the test needs no vocabulary of properties beyond the statement classification of §5.2, which a separate check applies to every delta file.

Equality through `create_table_query` has one known limit. The server prints a materialized view's declared columns from the query at `CREATE` time and updates them on `MODIFY QUERY`, so a view compares equal after the delta. A property that the server does not print, such as a comment, is not compared, and the templates declare none.

### 5.8 Operator path

```
jaeger ... --config config.yaml clickhouse-schema plan      # pending statements and ledger inserts, apply nothing
jaeger ... --config config.yaml clickhouse-schema apply     # apply every pending statement, additive and deferred, once
jaeger ... --config config.yaml clickhouse-schema render    # the rendered current templates
```

The `plan` command reads the ledger and prints every pending statement, rendered for the deployment, in the order the runner would execute it, with each file's ledger `INSERT` after its statements. It exits non-zero when anything is pending, so it can serve as a CI check or an init-container gate. It prints the pending runbooks by name. A database with `spans` and no ledger is treated as version 1, so the operator of a legacy database receives every version. The command needs `SELECT` on the ledger table and on `system.tables`, and nothing else. An operator who applies the printed statements by hand also applies the printed ledger inserts, which is what keeps the next `plan` empty.

The `apply` command runs the one-shot procedure of §5.5. It needs the `plan` grants, `INSERT` on the ledger, `ALTER` on the database's tables and `ALTER VIEW MODIFY QUERY` on its views, and `CREATE TABLE` plus `SELECT` and `INSERT` on the database for a version that creates a table or view, because `CREATE MATERIALIZED VIEW ... TO` requires both on its target. The lock table in §5.5 is read and written through the same grants. A multi-replica cluster needs `REMOTE ON *.*`, plus `CLUSTER` when `cluster` is set (§5.6). The command takes a lock where the server offers one, applies the pending additive and deferred statements in version and template order, verifies the additive ones on every replica, records each file, and exits non-zero if a runbook remains pending. The `--from <version>` flag re-applies the deferred statements of that version onward regardless of the ledger, for the case in §5.5.

The `render` command requires `table_engine` and says so when the setting is absent, because a rendered schema without engines is not one. The `apply` command is also the form for fleets that want the schema settled before pods roll: one job that runs before the rollout, such as a Helm pre-upgrade hook, and not a per-pod init container, which a rolling deployment runs once per pod and therefore concurrently across two releases.

All three commands render with `ttl`, `table_engine` and `cluster` from the configuration file. Their output therefore matches the deployment rather than a default. The collector owns the root `jaeger` command, which registers `--config` as a local flag. Cobra does not pass that flag to subcommands, so the subcommand declares the same `--config` flag and feeds it to the same configuration loader.

### 5.9 Tests

All tests except group 6 run against the live ClickHouse already started by the integration suite.

1. **Fresh install.** The test starts the backend on an empty database and checks that `plan` is empty afterwards and that the ledger holds every version. It also checks that the `create_table_query` of every object equals that of a database created by the templates alone.
2. **Equality from every snapshot.** The test of §5.7.
3. **Idempotence and concurrency.** The test starts the backend twice and also starts it concurrently from two connections. The plan must be empty after each case, and the ledger must hold each file once per instance that applied it. Against a two-replica table, the test runs `ADD COLUMN IF NOT EXISTS` concurrently through both replicas; both starts must succeed through the retry on error 517. Another case starts an instance built with one more version than the other against a legacy database; both must start, the older must ignore the newer rows, and the schema must be the newer one's.
4. **Legacy and operator-managed databases.** The test creates a database from `snapshots/001.sql` with no ledger, starts the backend, and checks that version 1 is recorded and every later version applied. It runs `plan` with the default `create_schema: false` configuration against the same database before the start and checks the printed statements and inserts, applies them by hand through `clickhouse-client`, and checks that the next `plan` is empty. Every `plan` and startup assertion uses a user with exactly the grants listed in §5.8, never `default`. A grant omitted from that list therefore fails the test rather than the operator's deployment.
5. **Deferred statements.** The test covers each deferred form in the vocabulary of §5.2. Startup must log it and leave it pending. The `clickhouse-schema apply` command must apply and record it, and `apply_deferred_changes: true` must do the same at startup. With `create_schema: false`, startup must issue no DDL and no ledger read at all. The test checks this through `system.query_log`. An operator-added index and a customized codec on an untouched column must survive both `apply` paths.
6. **Runner unit tests** use synthetic ledger rows and delta files. They cover statement splitting, classification of every form in the vocabulary and rejection of every form outside it, checksum-driven re-pending, version and file ordering, parameter rendering including `ON CLUSTER`, and extraction of the table and column or index name for verification.
7. **Lock and replication.** The lock tests run against ClickHouse with its embedded Keeper, which a single server supports. Two concurrent `clickhouse-schema apply` runs must leave one waiting. An expired lease must be taken over exactly once. A renewal racing a takeover must lose, and a release racing a successor must preserve the successor's row. Without `KeeperMap`, the command must report that fact and run unlocked. A two-replica Compose job covers convergence through `ON CLUSTER` and through a `Replicated` database. It also checks that `cluster` set on a `Replicated` database is reported. A replica down during startup must leave startup successful and receive the column when it returns. Verification must fail startup when a replica that answers still lacks a column.

The tests run against both the minimum ClickHouse version in §8 and the latest release. The CI ClickHouse already runs an embedded Keeper through `docker-compose/clickhouse/keeper.yaml`. Test 7 adds `keeper_map_path_prefix` to that configuration. The Compose job runs in the storage integration workflow with the other backends.

## 6. Upgrading an Existing Deployment

An existing deployment has the twelve objects created by the previous release and no ledger. The first start of a binary with this mechanism behaves as follows:

- With `create_schema: true`, the runner records version 1, applies version 2's ten `ADD COLUMN` statements to `spans`, and starts. If `ttl` is set, version 2 also carries a deferred `MODIFY TTL` on `spans` and `trace_id_timestamps`, because the `toDateTime(...)` wrapper of §8 changes the TTL expression. Startup logs it, and `clickhouse-schema apply` applies it.
- With `create_schema: false`, startup does nothing, exactly as today. Inserts fail until the operator applies the columns. The operator obtains the statements and the ledger inserts from `clickhouse-schema plan`, which the release notes name, instead of deriving them from a template diff.

Nothing in this upgrade touches an object or property that version 2 does not name. A hand-tuned `index_granularity`, an operator's skip index and a customized codec stay as they are. A `ttl` changed in the configuration since the tables were created is likewise left alone, because no delta names it; §8 lists a diagnostic for such drift as later work.

Grants are the way the upgrade can fail outright. A `create_schema: true` deployment whose Jaeger user has only the `CREATE TABLE` grant needed by today's startup fails to start, because the runner also needs `INSERT` on the ledger and `ALTER` on the tables. A multi-replica cluster needs `REMOTE`. A self-hosted `Replicated` database with a password on `default` needs a `collection_name` with cluster credentials (§5.6). A multi-replica cluster without fan-out is unsupported (§5.6). The release notes therefore list these requirements before the upgrade, and the startup error names the missing one.

## 8. Open Questions

- **Minimum ClickHouse version.** `MODIFY QUERY` no longer requires its experimental setting as of 23.11, and `keeper_map_strict_mode` became available in 23.4. The backend states no minimum version today. Three facts affect the choice. First, the current `event_attribute_metadata_mv` and `link_attribute_metadata_mv` fail to create on 24.3 through 24.12 under the default analyzer. The server returns `UNKNOWN_IDENTIFIER` for the nested attribute keys. The two views create on 25.3, so a fresh install needs 25.3 regardless of this RFC's decision. Second, a `Replicated` database requires an experimental setting on 24.3. Third, today's rendered TTL clauses are rejected with `BAD_TTL_EXPRESSION` on 24.3 through 25.3 and accepted on 25.12. These clauses are `start_time + INTERVAL n SECOND` over a `DateTime64(9)` column on `spans` and `end + INTERVAL n SECOND` over a `SimpleAggregateFunction(max, DateTime64(9))` column on `trace_id_timestamps`. This RFC proposes a minimum version of 25.3, documented with M1. Version 2 wraps the column in `toDateTime(...)` in both templates, and for existing databases the wrapper is a deferred `MODIFY TTL` rather than a rewrite, which keeps 25.3 rather than 25.12 as the floor.
- **`apply_deferred_changes` as a setting.** This setting lets a single-node installation retain today's hands-off behavior for every change. The alternative omits the setting and requires even single-node operators to run `clickhouse-schema apply` for deferred changes. That design is simpler but adds one operator step.
- **A validate-only startup mode.** A migration runner inside a server binary conventionally has three modes. It can apply changes at startup, validate at startup and fail or warn if the schema is behind, or do nothing. This design provides the first and third through `create_schema`. Reading the ledger costs one `SELECT`, so a third `create_schema` value that reads it and only logs is cheap. This RFC still proposes deferring it until an operator asks, because `clickhouse-schema plan` as an init container or CI step provides the same check today and §5.3 is simpler with two rows than with three.
- **Drift diagnostics.** The ledger does not reveal a difference made outside Jaeger, such as a `ttl` changed in the configuration after the tables were created. A `clickhouse-schema diff` command that compares the live `create_table_query` of each object with the rendered templates would report such differences without acting on them. It is deferred until there is demand, and nothing in this design prevents adding it.
