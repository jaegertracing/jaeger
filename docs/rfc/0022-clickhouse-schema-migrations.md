## Abstract

The ClickHouse backend creates its tables and materialized views at startup. It uses one `CREATE ... IF NOT EXISTS` template per object but cannot change an existing object. The missing OTLP span columns in #9789 are the first change that a release makes to the schema of existing users. That change therefore has to establish how the schema is amended from now on.

This RFC describes the current mechanism and the requirements for its replacement. It analyses five families of approach. The first uses a migration framework to apply versioned delta files, as #9789 sketches and #9796 implements with golang-migrate. The second applies the same deltas through a small in-house migrator over a frozen baseline. The third keeps a full schema copy per version, as the Cassandra backend does. The fourth keeps today's templates as the living schema for fresh installs and applies short per-object deltas to existing databases, either written by the contributor or generated by a diff tool as Atlas and Prisma do. The fifth uses reconciliation: the backend compares the live catalog with the templates at startup and computes the `ALTER` statements itself, in the manner of Kubernetes controllers and Terraform.

This RFC recommends the fourth family in its hand-authored form. The templates remain the readable source of truth and are edited in place. A PR that changes a template also adds one short delta file per changed object to the directory of the current schema version. A CI test proves that the previous version's schema plus the deltas equals the current templates, so the deltas are checked against the templates the way generated code is checked against its source. A small runner over the backend's existing ClickHouse connection records applied versions in a ledger table.

A version is applied as a whole, by one party. Each version declares itself automatic or operator-applied. An automatic version holds only statements that change metadata, rewrite no data and can be repeated safely. If every pending version is automatic and `create_schema` is true, the runner applies all of them at startup. If any pending version needs the operator, the runner applies none of them, and the binary refuses to start with an error that names the command to run. An upgrade is therefore never split between the binary and the operator, and the binary never serves traffic against a database that it knows to be behind.

A delta changes only the property it names. An index, column, codec or setting that an operator added by hand therefore survives every upgrade that does not name it. A newer recorded version never prevents an older binary from starting, so the previous release can restart during a rollback.

The RFC also defines the ClickHouse cluster setups that the backend supports and how each is configured (§6). Creating the schema for the first time is part of applying it, and one release has to create and amend the same objects on every node.

## 1. Motivation

Three conditions require a decision now.

1. **A schema change is pending.** #9789 adds ten columns to the `spans` table. Against an existing deployment, the startup statements are no-ops, so without a migration mechanism the columns never appear, and the writer fails on its first insert after the upgrade.
2. **RFC 0017 queues more.** Each codec, table setting and skip index adopted by RFC 0017 requires a metadata-only `ALTER TABLE`. Its `LowCardinality` wrappers change column types, which rewrites data and needs an operator procedure (§2.3). The backend will change its schema several times over the next few releases, and each change needs a defined path rather than its own procedure.
3. **Two PRs already implement one answer.** #9796 and #9799 adopt golang-migrate along the lines sketched in #9789. They place the entire baseline schema in a single `000001_initial_schema.up.sql`. Review of those PRs showed that the file layout, the test design and the library's fit need deciding before the code, which is what an RFC is for.

The Cassandra backend illustrates two problems to avoid. Its schema lives in `v001.cql.tmpl` through `v004.cql.tmpl` under [`internal/storage/v1/cassandra/schema/`](../../internal/storage/v1/cassandra/schema/), each a complete copy of every table. Upgrades are operator-run shell scripts in a `migration/` directory that the binary knows nothing about. Changing one table requires a new copy of the entire schema, and nothing records the version of a running keyspace. The ClickHouse mechanism has to improve on both properties.

## 2. Current State

### 2.1 Files and parameters

The schema has twelve files under [`internal/storage/v2/clickhouse/sql/`](../../internal/storage/v2/clickhouse/sql/), one per object: six tables (`spans`, `services`, `operations`, `trace_id_timestamps`, `attribute_metadata`, `dependencies`) and six materialized views that fill the derived tables from `spans`. The `queries.go` file embeds each as a string variable. The `newSchemaBuilder` function renders every file as a `text/template` document with the `schemaTemplateParams` type. The parameters come from the deployment's configuration, and they decide the shape of the schema as much as the files do:

| Configuration | What it changes in the rendered schema |
| --- | --- |
| `ttl` | the `TTL ... DELETE` clause on `spans` and `trace_id_timestamps`; zero renders none |
| `table_engine` (#9813) | the `ENGINE` clause of every table: `MergeTree` and `AggregatingMergeTree`, or their `Replicated*` counterparts |
| `attribute_layout` | the type of every attribute group on `spans`, `Nested(key, value)` or `Map(String, T)`, and the key expressions of the three attribute-metadata views. The two layouts are not convertible |
| `hoisted_attributes` (RFC 0017 §5.2) | one `MATERIALIZED` column on `spans` per configured entry |
| `table_engine.cluster` (§6; the layout is in review as #10089) | six `<table>_local` storage tables, six `Distributed` tables under the public names, and views that read `spans_local` and write `<table>_local` |

One release therefore renders several schemas. A migration mechanism has to change all of them from one description. The cluster terms used from here on, such as node, shard, replica, storage table and `Distributed` table, are defined in §6.1.

### 2.2 Startup behavior

With `create_schema: true`, the `NewFactory` function executes the rendered statements one by one over its ClickHouse connection, in dependency order, before the backend serves traffic. With `create_schema: false`, the operator owns the tables.

The backend records nothing about the statements it executes. It has no version table, and startup does not check whether the tables match the release's expectations in general. Two narrow checks exist, and both run under either value of `create_schema`. The `checkAttributeLayout` function reads the layout of the `spans` table and refuses to start when it differs from `attribute_layout`. The `checkHoistedColumns` function reads every configured hoisted column from `system.columns` and refuses to start when one is missing or differs. The error for a missing column contains the `ALTER TABLE` statement to run. The backend thus already has the rule that it does not start against a schema it knows to be wrong, and already has schema changes that only the operator applies.

Any other mismatch causes an insert or query error on the first request that touches the missing column.

### 2.3 What ClickHouse allows after `CREATE`

The parts of a table that can change in place determine the shape of a migration mechanism.

| Change | Statement | Cost | Replicated tables |
| --- | --- | --- | --- |
| Add a column | `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` | metadata only¹ | propagates through Keeper |
| Add a skip index | `ALTER TABLE ... ADD INDEX IF NOT EXISTS` | metadata only; existing parts are indexed on merge or by `MATERIALIZE INDEX` | propagates |
| Change a column's codec | `ALTER TABLE ... MODIFY COLUMN ... CODEC(...)` | metadata only; parts are re-encoded on merge | propagates |
| Replace a skip index | `DROP INDEX` then `ADD INDEX` | `DROP INDEX` is a mutation that only deletes index files; the new index is built on merge or by `MATERIALIZE INDEX` | propagates |
| Change a column's type, including adding `LowCardinality` | `ALTER TABLE ... MODIFY COLUMN ... <type>` | a mutation that rewrites every part² | propagates |
| Change a table setting | `ALTER TABLE ... MODIFY SETTING` | metadata only | replica-local³ |
| Change or remove TTL | `ALTER TABLE ... MODIFY TTL`, `ALTER TABLE ... REMOVE TTL` | a mutation by default; metadata only with `materialize_ttl_after_modify = 0`, after which the new expression applies as parts merge⁴ | propagates |
| Change a view's query | `ALTER TABLE <view> MODIFY QUERY` | metadata only | replica-local³ |
| Extend the sorting key | `ALTER TABLE ... MODIFY ORDER BY` | metadata only, and only by appending columns added in the same statement | propagates |
| Drop a column | `ALTER TABLE ... DROP COLUMN` | destroys data | propagates |
| Change `ENGINE`, `PARTITION BY`, or the existing sorting key | not possible | requires a new table and a copy | n/a |

- ¹ ClickHouse adds the column to each part's metadata. Existing parts have no value for it and evaluate the current default at read time until they merge. A later default change therefore changes the values read from those parts (§5.4).
- ² A mutation performs background work over every affected part. For a large `spans` table, this takes hours of I/O. A type change therefore never runs at startup (§5.2).
- ³ A `MODIFY SETTING` on a `Replicated*` table changes only the replica that receives it. The server code establishes this behavior: the `StorageReplicatedMergeTree::alter` method does not replicate an alter that changes only settings. The ClickHouse documentation does not state this restriction. A materialized view uses the `MaterializedView` engine, rather than a `Replicated*` engine, so its `MODIFY QUERY` is also local. Reaching every replica requires the fan-out described in §2.4.
- ⁴ With materialization off, an existing part keeps its rows and the TTL bounds recorded under the old expression until a merge rewrites it. A shortened TTL therefore reclaims a part that no longer merges only after an operator runs `ALTER TABLE ... MATERIALIZE TTL`. A `spans` partition that no longer receives inserts is such a part.

Replication does not cover all DDL. A column, index or codec `ALTER` on a `Replicated*` table is recorded in Keeper and applied on every replica of that shard. In contrast, `CREATE TABLE`, `MODIFY SETTING` and a view's `MODIFY QUERY` affect only the node that the client reaches. A `Distributed` table keeps its own column list and follows no `ALTER` of the storage table beneath it. Reaching the other servers requires `ON CLUSTER`, a database with the `Replicated` database engine, or a connection to each server. Section 6.3 applies this distinction to the design.

### 2.4 Facilities ClickHouse offers a schema tool

- **System catalogs.** The `system.tables` catalog provides `create_table_query`, the server's own normalized rendering of the whole object: columns in order, defaults, codecs, indexes, engine, keys, TTL and settings for a table, and the `SELECT` for a view. Two objects created on one server from equivalent DDL therefore print the same text, which makes equality of two schemas a string comparison without a SQL parser. One exception was measured (test A.10): the `SETTINGS` clause lists the settings in the order they were assigned, so a table that received a setting through `MODIFY SETTING` prints the clause in a different order from a table created with it (§5.7). The `system.columns` and `system.data_skipping_indices` catalogs provide each column and index by name.
- **DDL fan-out.** The `Replicated` database engine replays every DDL statement issued to one replica on all replicas. ClickHouse Cloud's `Shared` database engine builds on it and does the same for every database there. On a self-hosted cluster with an `Atomic` database, `ON CLUSTER <name>` provides the same fan-out per statement, and this design does not use it (§6).
- **No lock.** ClickHouse has no advisory locks. A `KeeperMap` table with `keeper_map_strict_mode = 1` provides a compare-and-set operation, but only on a server with a Keeper ensemble and the opt-in `keeper_map_path_prefix` setting, and it cannot revoke distributed DDL that a previous holder queued. The design therefore does not depend on a lock (§5.5).

### 2.5 How the other backends do it

Section 1 covers Cassandra. Elasticsearch and OpenSearch have no comparable problem. The binary installs their mapping as an index template at startup. Indices roll by day or by alias rollover, so a new mapping applies to the next index without altering the previous one. Badger and memory have no persistent schema.

## 3. Requirements

This RFC judges the mechanism against the following criteria, which also form the comparison rows in §4.6.

1. **Per-object deltas.** Changing one column of one table changes one short file. It never requires a schema copy.
2. **One source of truth.** A fresh install and an upgraded install derive their final schema from one set of files. A second description, if one exists, is checked against the first by CI rather than by contributor discipline, the way generated code is checked against its source.
3. **Template parameters survive.** The settings in §2.1 describe the deployment, rather than the schema. Every statement has to render them. A migration file that hard-codes `MergeTree` can silently give a replicated deployment local tables, which is a data-loss configuration.
4. **The database's state is knowable.** The binary and the operator can identify which Jaeger schema changes a database has received and which are pending.
5. **Safe with concurrent instances.** Several Jaeger instances start together against one database. The result has to be correct regardless of which instance finishes second.
6. **Operator-managed schema stays possible.** With `create_schema: false`, the operator applies DDL by hand. The binary gives the operator exactly the DDL to apply, rendered for that deployment.
7. **Readable current schema.** A developer changing the writer can read a file to see the current `spans` table. The developer does not have to replay its history.
8. **Small dependency footprint.** The backend adds no database drivers or connection paths that it does not otherwise use.
9. **Little bookkeeping imposed on contributors.** Each version number, ordering rule, frozen file and generated golden file adds something for a contributor to learn and a reviewer to check.
10. **What runs in production is reviewable.** A schema PR reviewer can see the statements that will execute. An operator can see them before an upgrade.
11. **Operator customizations survive.** An upgrade changes only what Jaeger's schema change names. It does not undo an index, column, codec or setting that an operator added by hand to anything else.
12. **Planning writes nothing.** Computing what the database lacks changes no live object and needs no privilege beyond `SELECT`.
13. **No split application.** A schema change is applied in full by one party, the binary or the operator. A database is never left with the part of an upgrade that was safe to automate and without the part that was not.

## 4. Approaches

### 4.1 Versioned deltas applied by a migration framework

Flyway, Liquibase, golang-migrate and goose use a numbered sequence of forward-only files. A table records which files have run, and a library applies pending files in order. This is the model sketched in #9789. The files together define the current schema: the baseline is version 1, and each change adds a file. #9796 implements this model with golang-migrate.

Two properties of golang-migrate affect this choice. First, the library does not constrain the layout. It reads each version as one `io.Reader` from any `fs.FS`, so the backend can render per-object files and concatenate them in memory. The single baseline file in #9796 is therefore a choice. Second, the ClickHouse driver fits this backend poorly. It requires a second connection through `database/sql`. Its process-local lock leaves concurrent instances dependent on idempotence alone. Its version-table handling and refusal to start against a newer recorded version each contradict a requirement in §3. The review of #9796 holds the specific objections. After workarounds for these problems, the library provides only the version table and the ordered walk, about a hundred lines of code.

### 4.2 Versioned deltas applied by an in-house migrator

An in-house migrator uses the same layout: a frozen baseline as version 1 and one directory per later version, with one file per object changed by that version. The backend implements the walk and version table over its native connection. This removes the driver problems above. The baseline, however, no longer describes the readable current schema. Contributors read a golden `SHOW CREATE TABLE` dump instead, and the templates of §2.1 stop being the schema and become one historical version of it.

### 4.3 Full copy of the schema per version

Cassandra uses a complete, readable schema for each version. The difference between two versions is whatever a human writes into a migration script. This model necessarily fails requirement 1 and records nothing in the database. It appears here because it is the repository's precedent.

### 4.4 Living templates for fresh installs, deltas for upgrades

This approach keeps today's templates as the readable current schema and edits them in place. A fresh install creates the tables from the templates. An existing database receives short delta files, one per changed object, that the PR commits alongside its template edit. A ledger table records which versions a database has received.

The deltas can come from two sources.

- **4.4a, hand-authored deltas.** The contributor writes the delta alongside the template edit. The two describe the same change twice, so a CI test creates one database from the previous version's schema plus the deltas and another from the current templates, and requires the server's `create_table_query` text of every object to be equal (§5.7). The test needs no vocabulary of properties, because equality of two objects created on the same server is a string comparison (§2.4). This is the check that makes the templates the single source of truth: a delta that does not reproduce them cannot merge, just as stale generated code cannot.
- **4.4b, generated deltas.** Atlas calls this the versioned workflow with `atlas migrate diff`; Prisma and Alembic use it too. A tool compares the templates with the previous version's schema and writes the delta. The contributor reviews and commits it. Generation needs a per-property diff engine that turns each difference into a statement, which is the same engine that reconciliation (§4.5) runs in production, moved to a developer's machine. Its output is also the first draft of a reviewed delta, so the two variants differ in tooling and not in what reaches production.

Both variants keep the version record, so the state of a database is the list of versions it has received. The version directory is opened once per release cycle rather than once per PR, so concurrent PRs add files to the same directory without a numbering conflict (§5.1). Because a version is an explicit, reviewed unit, each version can also carry a reviewed decision about who applies it, which is what makes requirement 13 enforceable (§5.2).

### 4.5 Reconciliation

Reconciliation describes the desired schema once, declaratively. The tool computes the statements needed to bring the live database to that state. Kubernetes controllers use this model for resources, Terraform uses it for infrastructure, and Atlas, Skeema, sqldef and Prisma use it for relational schemas. For ClickHouse, Atlas's ClickHouse driver, PostHog's `chschema`, Noibu's `housekeeper` and the Python `clickhouse-migrations` tool's `diff` command use this model. These tools run from a CLI at deploy time.

Reconcilers also have an established form that runs inside an application at startup, under the constraint that it removes nothing by default. Ent's `Schema.Create` method and GORM's `AutoMigrate` method inspect the live database and issue `CREATE TABLE`, `ADD COLUMN` and `ADD INDEX` for objects present in the Go schema but absent from the database, and GORM also alters a column whose size, precision or nullability changed. Neither drops a column or index unless the caller passes an explicit option, because a reconciler that converges exactly would read a rename as a drop plus an add.

For this backend, the templates would describe the desired schema. At startup, the backend would render them, create each table under a throwaway name in the same database, read the scratch and live objects from the system catalogs, and compare them per property. Scratch tables are needed because a session-scoped `CREATE TEMPORARY TABLE` reports empty keys, a bare engine and no indexes in the catalogs. The diff would apply the additive statements of §2.3 at startup, report the metadata-only non-additive ones for an operator command, and refuse the rest. Anything present in the live table but absent from the templates would be left alone.

This approach detects drift and gives an operator the exact statements their database lacks. It has four costs that the delta approaches do not share. The scratch tables make planning a write: every start creates and drops a copy of every table, needs `CREATE TABLE` and `DROP TABLE` grants, adds entries to a `Replicated` database's DDL log, and needs a sweep for scratch tables that a crashed run left behind. The comparison needs a vocabulary of every property it compares, with a fixed action per property, because a live difference has no label: an operator's customization, a partially completed upgrade and a schema created by the previous release all look alike in the catalog. An `apply` resets every customized codec, setting, default and TTL to the template on every run, so an operator who customizes one property cannot receive Jaeger's own changes without losing it. And the unit it acts on is a single difference rather than a release's change, so it applies whatever part of an upgrade is safe and leaves the rest, which is the split application that requirement 13 excludes.

### 4.6 Comparison

| 8. Dependency footprint | 🟨¹⁴ | 🟢 | 🟢 | 🟢 | 🟢 | 🟢 |
| 9. Little bookkeeping | ❌¹⁵ | ❌¹⁵ | 🟨²⁴ | 🟢¹⁶ | 🟢¹⁶ | 🟢¹⁶ |

| 13. No split application | 🟨²¹ | 🟢²¹ | 🟢 | 🟢²¹ | 🟢²¹ | ❌²² |
| Code to own²³ | 🟨 ~150 lines of glue and driver workarounds | 🟨 ~200 lines: runner and ledger | 🟢 none | 🟢 ~250 lines: runner, ledger and the equality test | ❌ ~250 lines plus a 600 to 900 line generator | ❌ 1200 to 1600 lines: per-property diff, generator, scratch lifecycle, replica verification |

🟢 meets the criterion; 🟨 meets it with a caveat; ❌ fails it.

- ¹ The library reads each version as one stream, so the backend can concatenate per-object files in memory. The single baseline file in #9796 is that PR's choice, rather than a framework constraint.
- ² The full schema copy describes the resulting state, and the human-written migration script that takes a database from the previous copy to it describes the transition. They are two descriptions, and nothing checks them against each other.
- ³ The deltas are a second description of each change, checked against the templates by the equality test of §5.7 on every PR. The test fails when a delta is missing, wrong or stale, so the templates remain the only description a contributor has to get right.
- ⁴ As it stands, #9796 renders the baseline through the templates; the earlier shape that its review commented on hard-coded the engine.
- ⁵ The ledger states which versions the database received and which are pending, which is the question an upgrade asks. It does not reveal a change made outside Jaeger, and under requirement 11 the mechanism must not act on one.
- ⁶ The live catalog determines the plan, so the report also includes drift. The report cannot say whether a difference is a customization, a partial upgrade or the previous release's shape.
- ⁷ The library does not create its version table idempotently, so first starts race. Pending versions can also interleave across instances.
- ⁸ Instances of one release execute identical idempotent statements and converge. Two different releases that both start against a database two or more versions behind can interleave statements that assign the same codec, setting, TTL or view query, and the older assignment can land last (§5.5).
- ⁹ Startup applies only additive statements, which commute.
- ¹⁰ golang-migrate applies files as stored. The operator receives the files and the message "versions 2 and 3 are pending", and renders the parameters by hand.
- ¹¹ The `plan` command renders the pending versions' statements with the deployment's configuration, followed by the ledger inserts that record them, so a hand-applied version is recorded (§5.8).
- ¹² The operator receives exactly the statements that the database lacks, computed against that database.
- ¹³ A generated golden dump provides the readable current schema, rather than the authored files.
- ¹⁴ The library's driver requires a second `database/sql` connection.
- ¹⁵ Contributors manage version numbers per PR, a frozen baseline and a golden dump, and follow a rule that released versions never change.
- ¹⁶ The contributor edits the template and, for 4.4a, writes the delta file in the open version's directory. Snapshots are produced by a `make` target when the next version opens, and CI enforces the immutability of closed versions and the equality of deltas and templates (§5.7). Reconciliation would need the same snapshots for its upgrade tests.
- ¹⁷ The PR shows the template edit rather than the `ALTER` statements. Only a release-time generated file and the printed plan show those statements.
- ¹⁸ A delta touches only the properties it names. A `MODIFY COLUMN ... CODEC` delta overwrites an operator's customization of that one column's codec once, and the PR that ships it can say so. A customization of anything the delta does not name survives.
- ¹⁹ Each `apply` resets every customized codec, setting, default or TTL to the template. An operator keeps a customization only by never running `apply`, which also forgoes Jaeger's own changes, or by adding an accepted-differences list that reintroduces the classification of footnote 6.
- ²⁰ A plan creates and drops scratch tables in the configured database (§4.5). This requires `CREATE TABLE` and `DROP TABLE` there and a sweep for abandoned tables.
- ²¹ A version is a unit, so the runner can apply all pending versions or none of them (§5.2). The stock golang-migrate walk applies versions one by one and needs that rule added around it.
- ²² The reconciler acts per difference. It applies the differences that are safe at startup and reports the others, so one upgrade is applied partly by the binary and partly by the operator.
- ²³ Estimates of production and CI code without tests. The equality test of 4.4a compares `create_table_query` strings and needs no property vocabulary. The generator of 4.4b and the diff of 4.5 are the same engine; 4.5 adds the scratch-table lifecycle and the replica verification that reads every compared property back.
- ²⁴ The bookkeeping is a full copy of the schema per change. The statements that run are a hand-written script outside the binary. A reviewer can read it, but nothing ties it to the copies, and whether it preserves an operator's customization depends on its author.

This RFC recommends option 4.4a. Rows 10 through 13 and the code-to-own row decide the choice. The statements that run in production are the statements a reviewer read in the PR. A delta changes only what it names, so an operator's customizations survive. Planning reads one ledger table. An upgrade is applied whole by one party. The production code is a runner and a ledger, and the CI check compares the server's own rendering of each object.

Option 4.4a scores below reconciliation on row 5 and on row 4's drift detection. The row 5 caveat needs two different releases to start at once against a database that is at least two versions behind, its effect is a stale codec, setting or view query rather than a missing column, and re-applying the version repairs it (§5.5). Drift detection is something requirement 11 forbids the mechanism to act on, and it can arrive later as a diagnostic command without owning production upgrades (§10). Option 4.4b differs from 4.4a only in tooling, so a generator can be added later if hand-written deltas prove error-prone, without changing the layout, the runner or the tests.

Several costs are shared by every option and therefore do not appear as differences in the matrix. Rolling deployments need the compatibility rules of §5.4 whether a version number or a diff drives the upgrade. Default changes can change the values read from old parts, and view changes can need a backfill, under every option. Replicated DDL needs a delivery mechanism (§6) and the completion contract of §5.6 under every option. Section 9 collects the limitations of the recommended option.

## 5. Design

### 5.1 Files

The template files keep their locations and names. They remain the complete description of the current schema and change in place when the schema changes. The OTLP columns in #9789 add ten lines to `create_spans_table.sql`, and RFC 0017's codecs change that same file.

Two directories join them under `internal/storage/v2/clickhouse/sql/`:

```
sql/
  create_spans_table.sql          # living templates, as today
  ...
  migrations/
    002/
      version.yaml                # mode: automatic
      spans.sql                   # statements that take spans from version 1 to version 2
    003/
      version.yaml                # mode: operator, with the procedure document
      spans.sql
  snapshots/
    001/                          # rendered templates at the close of version 1,
      nested.sql                  # one file per test configuration (§5.7)
      map.sql
      ...
```

A schema version is an integer. Version 1 is the schema that the last release before this mechanism creates, so it has no `migrations/` directory. The `spans` table has had its sorting key and skip indexes since v2.18. The queries of `event_attribute_metadata_mv` and `link_attribute_metadata_mv` changed in v2.19, and a database created by v2.18 keeps the older ones, because `CREATE ... IF NOT EXISTS` never replaces a view. Version 2 therefore carries a `MODIFY QUERY` for each view whose query changed between v2.18 and the last release before this mechanism. The statement does nothing to a database that already has the query and brings an older one to the shape of version 1. Releases up to v2.17 created a different schema, which no delta can turn into version 1: v2.15 and v2.16 sort `spans` by `trace_id`, and v2.17 has other view queries and four more skip indexes. The runner recognizes such a database by the `sorting_key` of `spans` and by the `idx_attributes_keys` index, and refuses to start against it (§9).

A new directory opens once per release cycle: the first schema PR after a release creates `migrations/<N>/` and writes `snapshots/<N-1>/` with the `make clickhouse-schema-snapshot` target, which renders the templates at that PR's base. Version N-1 is closed from that point: a release carried it, and its directory and snapshot no longer change. Later PRs in the same cycle add or extend files in the open directory. Two PRs that change different objects therefore never conflict, and two that change the same object conflict in one file, where a reviewer wants to see it. CI compares every closed directory and snapshot with the last release tag. It rejects a change to a snapshot, and it accepts a change to a closed delta file only when the file still renders the same statements for every configuration in that version's snapshot. A template parameter that arrives after a version closed, as the cluster parameters of §6 do, is added to the closed deltas under this rule. Versions are issued on `main` only, so a patch release carries no schema change (§9).

A delta file is a `text/template` document and renders with the same `schemaTemplateParams` value as the table templates. It therefore produces the right statements for each schema of §2.1 from one description:

```sql
ALTER TABLE spans{{ .LocalTableSuffix }} ADD COLUMN IF NOT EXISTS schema_url String;
{{- if .DistributedTables }}
ALTER TABLE spans ADD COLUMN IF NOT EXISTS schema_url String;
{{- end }}
```

The `LocalTableSuffix` parameter is the one that #10089 introduces, `_local` in the `Distributed` layout and empty otherwise. A column delta in that layout needs the second statement because a `Distributed` table keeps its own column list (§2.3). A delta that concerns an attribute group renders the column type through the `ColumnTypeFn` function, so it serves both attribute layouts, and a delta that applies to one layout only is wrapped in a condition and renders nothing for the other. Statements are separated by a semicolon at the end of a line, and a file holds the statements for one object in the order they execute. A file never references the ledger, which the runner maintains.

The `version.yaml` file states who applies the version:

```yaml
mode: operator                      # or: automatic
procedure: docs/clickhouse/schema-003.md   # required for operator
```

**Versions cover what a release changes, not what a deployment configures.** The choice of `ttl`, engine, attribute layout, cluster and hoisted attributes belongs to the configuration, and a change to one of them by the operator is not a version. Hoisted columns stay governed by RFC 0017 §5.2: the operator adds them, and `checkHoistedColumns` verifies them at startup. No delta names a hoisted column, and the ledger does not record them.

### 5.2 Automatic and operator versions

The pending set is every version that the binary carries and the ledger does not record. The runner treats the pending set as one unit:

- If every pending version is automatic, the runner may apply the whole set at startup.
- If any pending version is an operator version, the runner applies nothing, including the automatic versions before and after it, and the binary refuses to start. The operator applies the whole set with `clickhouse-schema apply` (§5.8).

The reason for the all-or-nothing rule is that a partly applied upgrade is a state that neither party owns. The binary would be running on a schema that no release was tested against, and the operator would have to work out which statements remain. With the rule, the question "who upgrades this database" has one answer per upgrade. A failure can still interrupt a version part-way, and the party that started it resumes it (§5.8).

A version is automatic only if every statement in it has one of the following forms. A CI test parses every delta file of an automatic version and rejects any other statement.

| Form | Notes |
| --- | --- |
| `CREATE TABLE IF NOT EXISTS` | a new table; renders the deployment's engine |
| `CREATE MATERIALIZED VIEW IF NOT EXISTS` | a new view |
| `ALTER TABLE <t> ADD COLUMN IF NOT EXISTS` | one column per statement; `AFTER` is allowed |
| `ALTER TABLE <t> ADD INDEX IF NOT EXISTS` | existing parts are indexed as they merge |
| `ALTER TABLE <t> MODIFY COLUMN <c> CODEC(...)`, `... REMOVE CODEC` | takes no type, so it never rewrites data |
| `ALTER TABLE <t> MODIFY SETTING` | replica-local (§2.3) |
| `ALTER TABLE <t> MODIFY TTL ... SETTINGS materialize_ttl_after_modify = 0` | the setting is mandatory; without it the statement is a mutation |
| `ALTER TABLE <v> MODIFY QUERY` | replica-local (§2.3); subject to rule 3 of §5.4 |

Each of these changes only metadata, completes in seconds on a table of any size, and leaves the same result when two instances of one release execute it. The list is a ceiling and not a classification: a reviewer marks a version `operator` whenever its change needs a human decision, even if every statement has an automatic form. A view change that needs a backfill is such a case.

An operator version may hold any statement. It holds, for example, a type change such as `LowCardinality`, a `DROP INDEX` with the `ADD INDEX` and `MATERIALIZE INDEX` that replace it, a default change, a `MODIFY ORDER BY`, or a backfill. Its `procedure` document states what the statements cost, the order in which to run them and how to observe their completion. The `apply` command executes the version's statements in order and waits for each, so a long mutation is run by the same command that records the version. The ledger records a version file by file, so an interrupted `apply` resumes at the first unrecorded file and executes that file again from its first statement. The procedure document therefore states, for every statement that cannot be repeated safely, how to detect a partial result and remove it before the rerun. A backfill by `INSERT ... SELECT` is the common case.

Two consequences follow for how changes are grouped. A release that wants its metadata-only tuning to reach `create_schema: true` users without an operator step ships it in a release that carries no operator version. And one operator version blocks every later automatic version until the operator applies it, so an operator version is a decision to require an operator step from every deployment that upgrades across it.

### 5.3 The runner

```go
// schemaRunner applies the pending schema versions under
// sql/migrations to the live database and records them in the ledger table.
type schemaRunner struct {
    conn   driver.Conn
    params schemaTemplateParams
}

// plan only reads the ledger and the system catalogs, so it needs no write grant.
func (m *schemaRunner) plan(ctx context.Context) (schemaPlan, error)

// applyPlan records a file only after its statements succeeded and their result
// was verified on every replica, so a failed run leaves the file pending.
func (m *schemaRunner) applyPlan(ctx context.Context, plan schemaPlan) error

type schemaPlan struct {
    Versions []pendingVersion
}

func (plan schemaPlan) isAutomatic() bool

type pendingVersion struct {
    Version      int
    Mode         versionMode // automatic or operator
    ProcedureDoc string      // path of the procedure document, for operator versions
    Files        []pendingFile
}

type pendingFile struct {
    Object     string
    Checksum   string   // of the file before rendering
    Statements []string // rendered
}
```

#### The ledger

```sql
CREATE TABLE IF NOT EXISTS jaeger_schema_migrations (
    version        UInt32,
    object         LowCardinality(String),
    checksum       String,
    jaeger_version String,
    applied_at     DateTime DEFAULT now()
) ENGINE = {{ .MergeTree }}
ORDER BY (version, object, applied_at)
```

The ledger is a storage table on every node, rendered with the deployment's engine and never wrapped in a `Distributed` table. The runner inserts into the table on the node it is connected to. On a cluster it reads the ledger through `clusterAllReplicas`, over the cluster that §5.6 chooses, and takes the union of the rows of every node that answers. A row is therefore visible to every binary as soon as it is inserted, whichever node the binary is connected to, without waiting for replication and without a quorum. If the only node that holds a new row is down, another binary sees the file as pending and executes it again, which the automatic forms tolerate.

The ledger is insert-only. Version 1 has no rows. A file is pending when the ledger holds no row for its version and object, and a version is pending when any of its files is. For the highest version that the binary carries, the row also has to match the file's current checksum. That version is the open one in a build from trunk, where a later PR can extend a file that a fleet deployed from trunk has already applied, and the changed file is then pending again. Nothing in the ledger ever has to be updated or deleted.

The ledger records what was applied. It does not certify that a binary can run. An older binary therefore ignores rows for versions it does not know, and the previous release restarts during a rollback against a database that a newer release upgraded. Rule 1 of §5.4 is what keeps that database usable for it.

#### Startup

The steps below run before the backend serves traffic, under both values of `create_schema`.

1. The runner reads `system.tables` for the `spans` table and the ledger table before it creates anything, and classifies the database:
   - Without `spans`, the database is a fresh install.
   - With `spans` and a ledger whose only row is the fresh-install marker of step 2, it is a fresh install that an earlier start left incomplete.
   - With `spans` and a ledger that is absent or empty, the database was created before this mechanism and holds version 1, provided that it passes the baseline check of §5.1.
   - Otherwise the database holds the versions that the ledger records.
2. On a fresh install with `create_schema: true`, the runner creates the ledger table and inserts a marker row with version 0, which states that this release is creating the database from its templates. It then executes the current templates and records every version that the binary carries, automatic and operator alike, in one `INSERT`, which ClickHouse applies as one block. It executes no delta. The templates already describe the newest version, and a delta of an earlier version executed over them would put back a codec, setting or view query that a later version replaced. The marker is written before `spans` exists, so a start that dies at any point of this step is recognized by the next start and completed.
3. On any other database the runner executes no template. A new table or view reaches an existing database through a `CREATE ... IF NOT EXISTS` statement in a delta, like any other change. Nothing is therefore created before the pending set is judged.
4. The runner computes the plan from the ledger. An empty plan lets startup continue, and a database at version 1 with an empty plan needs no ledger.
5. With `create_schema: true` and a plan in which every version is automatic, the runner applies the plan. On a database without a ledger it first creates the ledger table. It applies the versions in order, and within a version in template order with tables before the views that read them. For each file it executes the statements, retries a statement on error 517 (§5.5), verifies the result on every replica (§5.6), and only then inserts the ledger row. A file whose verification fails therefore stays pending, and the next start applies it again. The runner executes its whole plan even if another instance records some of it meanwhile (§5.5).
6. In every other case with a non-empty plan, the binary writes nothing and fails to start. The error lists the pending versions, names the procedure document of each operator version, and gives the `clickhouse-schema plan` and `apply` command lines.

| `create_schema` | Pending versions | Behavior |
| --- | --- | --- |
| either | none | Start. |
| `true` | fresh install | Create the ledger and the tables, record every version, start. |
| `false` | fresh install | Fail to start. The `render` command prints the statements to run (§5.8). |
| `true` | all automatic | Apply all, verifying and recording each file, then start. |
| `true` | at least one operator version | Apply nothing. Fail to start with the operator instructions. |
| `false` | any | Apply nothing. Fail to start with the operator instructions. |
| either | the ledger cannot be read | Fail to start. |

With `create_schema: false` the binary reads the ledger and the system catalogs and writes nothing. On a cluster the ledger read needs the `REMOTE` grant (§5.6). This is the same contract as the `checkHoistedColumns` function (§2.2): the operator owns the DDL, and the binary refuses to run against a schema it knows to be behind. Failing at startup with the statements to run replaces today's failure on the first insert.

The refusal is deliberately strict. It also blocks a release whose pending operator version is pure tuning that the binary could run without. A softer rule for such versions, in which the binary starts and warns, can be added later without changing the layout or the ledger (§10).

### 5.4 Rules for changing the schema

1. **Expand only.** A template edit adds columns, indexes, codecs and settings or changes a view's query. It never removes or renames a column read or written by the previous release. A removal changes the template in the release after the one that stops using the column, and it is an operator version. During a rolling deploy and after a rollback, an older binary therefore always runs against a schema that is a superset of its expectations. The existing `INSERT` statements with explicit column lists and `SELECT` statements with explicit columns already tolerate that schema.
2. **A change that rewrites data is an operator version, and it keeps the previous release working.** Column types, sorting keys, partition keys and engines change only in operator versions. Column type changes include `LowCardinality` and any change inside the attribute groups. The previous release restarts during a rollback, so the result has to remain writable by it. Widening a type to `LowCardinality` meets this requirement. Narrowing a type does not, and neither does `Nullable`: the previous release's reader scans the column into a Go value that cannot hold a `NULL` written by the newer release. A version also never adds a column or index with a definition that differs from one an earlier version added.
3. **A view change is forward-only and must leave old rows valid.** `MODIFY QUERY` and `CREATE` of a missing view affect only rows inserted afterwards. They repair no rows already in the target table. An automatic view change may therefore add derived columns, for which old rows hold defaults, or change the query if existing target rows remain correct under the new definition. A change to grouping, filtering or aggregation that makes old rows wrong is an operator version with a backfill that repopulates the target from `spans`. A version never drops and recreates a view, because inserts during the gap would bypass it.
4. **Defaults are semantics, not metadata.** A new column takes its type default. An `INSERT` from a binary that does not know about the column therefore still succeeds. Changing an existing column's `DEFAULT` requires only metadata changes to execute, but it changes the data read. Parts written before the column existed hold no value for it and evaluate the current default, while parts that materialized the column retain the old value. Thus, a row's value depends on its part's history. A default change is therefore always an operator version, and its procedure runs `ALTER TABLE ... MATERIALIZE COLUMN` first unless every such row is correct under the new default.

### 5.5 Concurrency

Concurrent instances of one release compute the same plan and execute the same statements. Every automatic form of §5.2 leaves the same result when executed twice, and the ledger is insert-only, so the instances converge and the ledger holds one row per file per instance that applied it. Each instance executes its whole plan and skips nothing that another instance recorded after the plan was computed. If two versions in the plan assign the same property, each instance issues the newer assignment after its own older one, so the last assignment to reach the server comes from the newest version. A duplicate `ADD COLUMN IF NOT EXISTS` normally does nothing. However, on a `Replicated*` table reached concurrently through two replicas, it can fail with `CANNOT_ASSIGN_ALTER` (error 517, "metadata on replica is not up to date"). The server's message states that the error can be retried. The losing statement did not execute, and the losing instance has to see its own statement applied before verification. The runner therefore retries every statement with backoff on that error for up to a minute. If retries expire, startup fails, and the next start plans again.

A rollback does not undo anything. The previous release has no statement for a version it does not know, so its restart leaves the newer schema as it is.

One case does not converge. Suppose the database is at version N-2 and two releases start at once, one carrying version N-1 and one carrying N-1 and N. Both have N-1 pending. If versions N-1 and N both assign the same codec, setting, TTL or view query, the older release's N-1 statement can execute after the newer release's N statement, and the N-1 value stands while the ledger records N. The case needs a fleet that runs two releases at once against a database that neither has upgraded. Its effect is a stale value of a metadata property; a column or index is never lost, because additions commute. The `clickhouse-schema apply --reapply-from <version>` command executes the statements of that version onward again and repairs it.

Two different releases that start at once against an empty database are a harsher form of the same case. The newer release can lose the `CREATE` race for a table and still record every version, including an operator version that nothing applied. The same command with `--reapply-from 2` repairs this database too, and a fleet avoids the case by creating a database with one release.

Operator versions are applied by `clickhouse-schema apply`, which this RFC designs to run once, from one place, as a pre-upgrade job. ClickHouse offers no lock that would enforce this (§2.4), so the instruction is the guarantee. A `KeeperMap` guard rail against two simultaneous runs is listed in §10.

### 5.6 Verifying every node

A statement that Jaeger issues has to take effect on every node of the setup (§6). The verification below, and the ledger read of §5.3, need a cluster that lists every node:

- On an `Atomic` database they read through the cluster named by `cluster.name` when the configuration has a `cluster` block, and the connected node only when it has none. Such a database has several nodes only with `create_schema: false`, where the operator applies the plan, ledger inserts included, on every node.
- On a `Replicated` database they read through the database's own cluster. That cluster connects with the credentials that the database's `collection_name` setting points to, which is a set of connection credentials stored in the server configuration, or as `default` with no password when there is none. A database with a password on `default` therefore needs such credentials.
- On a `Shared` database they read through the cluster named `default`.

The runner sets `alter_sync = 1` explicitly on every `ALTER`, because ClickHouse Cloud ships `0` as its default on several releases. An `ALTER` on a `Replicated*` table is executed on one replica of each shard, and the other replicas apply it afterwards. The statement can therefore return before the replica connected to Jaeger has the column. The runner does not rely on a stronger wait mode. With `alter_sync = 2` an active replica can delay completion without a bound and a down replica raises `UNFINISHED`.

The runner therefore verifies what it applied before Jaeger serves traffic. The statement forms that add an object name the table and the column or index, so the runner extracts those names and reads `system.tables`, `system.columns` and `system.data_skipping_indices` through `clusterAllReplicas`, over the cluster chosen above, always with `skip_unavailable_shards = 1`. This covers every shard and replica, and in the `Distributed` layout both the storage table and the `Distributed` table. A `MODIFY SETTING` and a view's `MODIFY QUERY` add no named object, and table replication does not carry them: only the database delivers them to the other nodes (§2.3). For these the runner reads the object's `create_table_query` from every node and requires each to equal the text on the node it is connected to. The check confirms presence by name and does not compare definitions, so a column that an operator created earlier under the same name with another type passes it (§9). Verification repeats with backoff for up to a minute while an object remains absent on a node that answers. If it remains absent after that minute, startup fails, because a node that still lacks a column would fail the first insert routed to it. The next start plans again. The `clusterAllReplicas` function needs the `REMOTE ON *.*` grant, and it connects to other nodes with the credentials in `remote_servers`, or as the initiating user if the cluster definition there has a shared `secret`. Jaeger's documentation has to say so.

A down node is neither certified nor fatal. It applies the queued DDL when it returns, but it accepts connections before its queue reaches the entry, and an insert routed there in that window fails with `NO_SUCH_COLUMN_IN_TABLE`. A fleet that cannot accept this window runs `clickhouse-schema apply` as a pre-upgrade job while every node is up.

A `Replicated*` table executes alters in order. A statement that arrives during a mutation from an operator version on that table waits for the mutation to finish, which for `spans` takes hours. This cannot happen at startup. A pending operator version stops the binary before it issues any statement, and the `apply` command records an operator version only after its mutations have finished on every replica (§5.8).

A multi-node deployment on an `Atomic` database receives no automatic version, because Jaeger refuses `create_schema: true` there from the first release that carries a version (§8). The `clickhouse-schema apply` command refuses it for the same reason, since it would reach one node. The operator runs the output of `clickhouse-schema plan` on every node.

### 5.7 Snapshots and the equality test

One release renders several schemas (§2.1), so the snapshot of a version is a directory with one file per test configuration. A Go table in the test package names the configurations and is shared by the `make clickhouse-schema-snapshot` target and the test:

| Name | Configuration |
| --- | --- |
| `nested` | `merge_tree`, `attribute_layout: nested`, `ttl: 0` |
| `map` | `merge_tree`, `attribute_layout: map`, `ttl: 0` |
| `nested-ttl-hoisted` | `nested` with `ttl` set and two hoisted attributes |
| `nested-replicated` | `replicated` in a `Replicated` database on a single node with the embedded Keeper and the macros of #9813, `attribute_layout: nested` |
| `nested-distributed` | `replicated` in a `Replicated` database, `table_engine.cluster` |

The package already keeps rendered schemas as golden files under `snapshots/TestSchemaBuilder_AttributeLayout/`; the version snapshots use the same rendering. The binary never reads a snapshot. Operators obtain executable statements from `clickhouse-schema plan`.

The equality test runs on every PR against the live ClickHouse of the integration suite. For each closed version N and each configuration, it:

1. creates database A from `snapshots/<N>/<configuration>.sql` and applies every version from N+1 through the open one in order, rendered for that configuration, automatic and operator alike;
2. creates database B from the current templates with the same configuration;
3. reads `create_table_query` from `system.tables` for every object in both databases, replaces the database name, sorts the entries of each `SETTINGS` clause, and requires the strings to be equal;
4. inserts the integration corpus into database A from `snapshots/<N>/corpus.sql` before step 1's deltas run, and reads it back with the current reader after they run. The file holds the `INSERT` statements that the writer of version N produced for the corpus, and the `make` target writes it with the snapshot, so the test needs no old binary. Catalog equality alone does not show that rows written before the upgrade remain valid under the new view queries and types.

A template edit without a matching delta fails step 3, and so does a delta without a matching template edit. Apart from the order of settings (§2.4), step 3 is a string comparison, so the test needs no vocabulary of properties. The hoisted configuration proves that a delta leaves configured columns alone. The `nested-distributed` configuration needs the multi-node harness of #9887 and joins the test when that harness exists.

A configuration that is added after a version closed has no snapshot for that version, and the test covers it from the first version that has one. The configurations exercise each parameter of §2.1 at least once and not every combination of them. A delta whose rendering depends on two parameters at once adds a configuration for that combination. The number of database pairs is the number of closed versions times the configurations times two servers. Each pair is DDL and a small corpus on empty tables. This RFC sets no limit on how old a database an upgrade supports, so every version stays in the test until one is set (§10).

The test runs against both ClickHouse 26.3, the earliest release that Jaeger supports, and the latest release, because the server's rendering of `create_table_query` is the comparison, and a server version can change it. A property that the server does not print, such as a comment, is not compared, and the templates declare none.

### 5.8 Operator path

```
jaeger ... --config config.yaml clickhouse-schema plan      # pending statements and ledger inserts, apply nothing
jaeger ... --config config.yaml clickhouse-schema apply     # apply every pending version, in full
jaeger ... --config config.yaml clickhouse-schema render    # the rendered current templates
```

The `plan` command reads the ledger and prints every statement of every pending version, rendered for the deployment, in the order the runner would execute it, with each file's ledger `INSERT` after its statements. It marks each version as automatic or operator and prints the path of each procedure document. It exits non-zero when anything is pending, so it can serve as a CI check or a deployment gate. A database with `spans` and no ledger is treated as version 1, and the output then begins with the ledger's `CREATE TABLE`. The command needs `SELECT` on the ledger table and on `system.tables`, `system.columns` and `system.data_skipping_indices`, plus `REMOTE ON *.*` on a cluster, and nothing else. An operator who applies the printed statements by hand also applies the printed ledger inserts, which is what lets the binary start.

The `apply` command applies the whole plan, operator versions included, and is the only way an operator version is applied by Jaeger. It executes each statement in order with `mutations_sync = 2` and `alter_sync = 2`. In a `Replicated` database a statement can still return when the node that received it has finished and the other shards have not, so after each statement the command reads `system.mutations` on every node and waits until no mutation of that table is unfinished. A node that is down fails the run. The command is a job for a time when every node is up. It verifies the added objects on every node (§5.6), and records each file. If a statement fails, the command stops, and the files recorded so far stay recorded; the next run resumes with the first file that is not, from that file's first statement (§5.2). It needs the `plan` grants, `INSERT` on the ledger, `ALTER` on the database's tables and `ALTER VIEW MODIFY QUERY` on its views, and `CREATE TABLE` and `CREATE VIEW` plus `SELECT` and `INSERT` on the database for a version that creates a table or view. An operator version can need more, such as `DROP` or `TRUNCATE`, and its procedure document lists what it needs. A cluster needs `REMOTE ON *.*`. The `--reapply-from <version>` flag executes that version onward again regardless of the ledger, for the cases in §5.5. The procedure documents of the operator versions in that range apply to the rerun as they do to an interrupted run.

The `apply` command is also the form for fleets that want the schema settled before pods roll, whatever the versions' modes: one job that runs before the rollout, such as a Helm pre-upgrade hook, with `create_schema: false` in the pods. This is the least-privilege configuration, because the pods then need only `INSERT` and `SELECT`. A per-pod init container is not a substitute, because a rolling deployment runs it once per pod and therefore concurrently across two releases.

The `render` command prints the current templates, the ledger's `CREATE TABLE`, and a ledger `INSERT` for every version that the binary carries. A database created from its output is therefore recorded as current. All three commands require `table_engine` and say so when the setting is absent. This holds under `create_schema: false` too, where the backend otherwise ignores the setting, because the ledger and any table that a version creates render with it. All three commands render with the deployment's configuration file, so their output matches the deployment rather than a default. The collector owns the root `jaeger` command, which registers `--config` as a local flag. Cobra does not pass that flag to subcommands, so the subcommand declares the same `--config` flag and feeds it to the same configuration loader.

### 5.9 Tests

Groups 1 through 5 run against the live ClickHouse already started by the integration suite. Group 6 needs no server, and group 7 runs in multi-node Compose jobs.

1. **Fresh install.** The test starts the backend on an empty database and checks that `plan` is empty afterwards and that the ledger holds every version, operator versions included. It also checks that the `create_table_query` of every object equals that of a database created by the templates alone. A start interrupted after the marker row, after the templates, and before the version rows must each be completed as a fresh install by the next start. A legacy database with an empty ledger table must be treated as version 1.
2. **Equality from every snapshot.** The test of §5.7.
3. **All or nothing.** With a pending set of automatic versions, startup with `create_schema: true` must apply and record all of them. With an operator version anywhere in the pending set, startup must fail, and `system.query_log` must show no DDL and no ledger insert from it, including for the automatic versions that precede the operator version. After `clickhouse-schema apply`, the same binary must start. With `create_schema: false`, startup must fail on any pending version and issue no DDL.
4. **Legacy and operator-managed databases.** The test creates a database from `snapshots/001/` with no ledger, starts the backend, and checks that the pending automatic versions are applied and recorded. A database created from the v2.18 templates must end with the view queries of version 1. A database created from the v2.16 or the v2.17 templates must be refused by the baseline check. It runs `plan` against the same kind of database, applies the printed statements and inserts by hand through `clickhouse-client`, and checks that the next `plan` is empty and that the binary starts with `create_schema: false`. Every assertion uses a user with exactly the grants listed in §5.8, never `default`. A grant omitted from that list therefore fails the test rather than the operator's deployment.
5. **Concurrency, rollback and customizations.** The test starts the backend twice and also concurrently from two connections; the plan must be empty after each case. With two versions that assign different codecs to one column, the newer codec must stand after two concurrent starts, with the statements of the two instances interleaved by the test. A binary built with one version fewer must start against a database that the newer binary upgraded and must leave the schema unchanged. An operator-added index and a customized codec on a column that no delta names must survive `apply`. A failed statement in `apply` must leave the earlier files recorded and the next run must resume. A failed verification must leave the file unrecorded.
6. **Runner unit tests** use synthetic ledger rows and delta files. They cover statement splitting, the automatic-form check on every form of §5.2 and on forms outside it, the pending-set rule, checksum-driven re-pending of the highest version only, version and file ordering, rendering for every configuration of §5.7, and extraction of the table and column or index name for verification.
7. **Clusters.** A two-replica Compose job covers setup 2 on a `Replicated` database. A two-shard job with two replicas per shard covers setup 3a, and with one node per shard setup 3b: placement by the sharding key, an acknowledged insert being stored on its shard, and each startup check of §6 under both values of `setup_validation`. Two concurrent starts through different replicas must both succeed through the retry on error 517. A replica down during startup must leave startup successful and receive the column when it returns. A binary connected to one replica must see a ledger row inserted through the other before replication delivers it. A `MODIFY QUERY` that one replica lacks must fail verification. Verification must fail startup when a replica that answers still lacks a column.

The tests run against both ClickHouse 26.3, the earliest release that Jaeger supports, and the latest release. The Compose job runs in the storage integration workflow with the other backends.

## 6. Cluster Setups

This section defines the ClickHouse deployments that Jaeger supports, how each is configured, and how a schema statement reaches every node. It replaces the proposal recorded on [#9886](https://github.com/jaegertracing/jaeger/issues/9886).

### 6.1 Terms

| Term | Meaning |
| --- | --- |
| Node | One ClickHouse server. |
| Shard | A part of the data. Every row belongs to exactly one shard. |
| Replica | A node that is listed for a shard. A shard has one replica or several. When it has several and its tables use a `Replicated*` engine, the replicas copy each other's rows. |
| Keeper | The coordination service of a ClickHouse cluster, either ClickHouse Keeper or ZooKeeper. Replicated tables and `Replicated` databases register in it and use it to agree on the order of changes. The rows themselves are copied directly between nodes. |
| Cluster | A named grouping of shards and their replicas, which ClickHouse can address as a whole. An administrator defines a cluster in the server configuration (`remote_servers`). |
| Storage table | A table that owns stored rows, such as a `MergeTree` or `ReplicatedMergeTree` table. |
| `Distributed` table | A table that owns no stored rows. It forwards an insert to the storage table on one shard, which it selects by the value of an expression called the sharding key. It runs a query on the storage tables of every shard and merges the results. |
| Public name | The table name that the reader and the writer use, such as `spans`. |
| Macro | A named value that the ClickHouse administrator defines in the server configuration of a node, such as `shard` and `replica`. Where the Keeper path or replica name of a table contains `{shard}` or `{replica}`, ClickHouse puts that node's value in its place. |
| `Atomic` database | A database with the default engine, `Atomic`. The database delivers no statement to other nodes. A `Replicated*` table in it still passes column, index and codec changes to its replicas (§2.3). ClickHouse runs a statement on every node of a cluster only when the statement carries `ON CLUSTER <name>`. |
| `Replicated` database | A database created with the `Replicated` engine on several nodes. Each node creates it with the same Keeper path and with its own `shard_name` and `replica_name` arguments, which say which shard the node belongs to and which replica of that shard it is. ClickHouse runs every statement that creates or alters a table in it on all of those nodes. ClickHouse also lets those nodes be addressed as a cluster that has the database's name, without an entry in `remote_servers`. This RFC calls it the database's own cluster. |
| `SharedMergeTree` | The storage engine of ClickHouse Cloud. Its rows are kept once in object storage, and every node reads and writes that one copy. The service substitutes it for `MergeTree` in a `CREATE TABLE` statement, and likewise `SharedAggregatingMergeTree` for `AggregatingMergeTree`. |
| `Shared` database | The database engine of ClickHouse Cloud, which the service gives to every database. Like a `Replicated` database, it runs every statement that creates or alters a table on all nodes. Its nodes are addressed as the cluster named `default`. |

### 6.2 Where the data lives

|     | Setup | Description | Storage engine | `Distributed` tables |
| --- | --- | --- | --- | --- |
| 1.  | Single node | One node holds all data. | `MergeTree` | no |
| 2.  | Replicas only | Several nodes, and each holds a full copy of all data. There is one shard. | `ReplicatedMergeTree` | no |
| 3a. | Shards with replicas | The data is divided into shards, and each shard has more than one replica. | `ReplicatedMergeTree` | yes |
| 3b. | Shards without replicas | The data is divided into shards, and each shard is one node. Losing a node loses that shard's data, so this setup is discouraged. | `MergeTree` | yes |
| 4.  | Shared storage | ClickHouse Cloud. The data is stored once, and every node reads and writes that one copy. | `SharedMergeTree` | no |

Each setup has its own subsection below, with the exact Jaeger configuration, what Jaeger creates, what the ClickHouse administrator has to set up on the servers, and the misconfigurations that Jaeger detects. The ClickHouse administrator is whoever configures the ClickHouse servers, and can be the same person as the operator who runs Jaeger.

### 6.3 Who delivers a statement to the other nodes

Setups 2, 3a and 3b have several nodes, and every node needs the same tables. Jaeger does not deliver its `CREATE` and `ALTER` statements to the other nodes itself. With `create_schema: true` it requires a database that does:

- **A `Replicated` database** delivers every statement to all of its nodes. Setups 2, 3a and 3b therefore require one. It rejects `Replicated*` engines with explicit arguments by default, so `table_engine.replicated` is used without `keeper_path` or `replica_name`.
- **A `Shared` database** does the same on ClickHouse Cloud.
- **An `Atomic` database** delivers nothing to other nodes. A `CREATE`, a `MODIFY SETTING`, a view's `MODIFY QUERY`, and any `ALTER` of a table that is not `Replicated*` run only on the node that receives them (§2.3). Jaeger supports it with `create_schema: true` for setup 1 only.

Jaeger does not add `ON CLUSTER` to its statements. The proposal on #9886 used it to reach the nodes of an `Atomic` database, and it is dropped here. It would give every setup a second configuration, add a parameter to every template and delta, and need a `CLUSTER` grant, in order to do what a `Replicated` database does without any of them. No Jaeger release has emitted `ON CLUSTER`, so no deployment depends on it.

A multi-node deployment on an `Atomic` database remains possible with `create_schema: false`. The operator runs the output of `clickhouse-schema render` and `plan` on every node. ClickHouse refuses a `Replicated*` engine without arguments in an `Atomic` database (test A.9), so this deployment sets `keeper_path` and `replica_name` in Jaeger's `replicated` block, with a path that does not contain `{uuid}`, such as `/clickhouse/tables/{shard}/{database}/{table}`. Tables created node by node have different UUIDs and would not find each other under a path that contains one.

Jaeger issues schema statements with `distributed_ddl_output_mode = 'throw_only_active'`, which waits for the nodes that are up and reports a failure on any of them. In contrast, `throw` waits the full `distributed_ddl_task_timeout` for a node that is down.

### 6.4 Startup checks

Jaeger checks the configuration against the deployment at every start, before it creates or alters anything. The checks only read. They take the database engine from `system.databases`, and the shards and replicas of the named cluster and of the database's own cluster from `system.clusters`. They read `system.macros`, `system.clusters` and `serverUUID()` from every node, through `clusterAllReplicas` over the named cluster or the database's own cluster, which needs the `REMOTE` grant (§5.6). A node that does not answer is left out of a check and does not fail it. A failed check stops startup with an error that names the setting, what Jaeger found in the deployment, and the setup that the deployment appears to be. Each subsection lists the checks under "Jaeger validation", with the outcome of each check and what Jaeger cannot detect.

Two checks apply wherever a `cluster` block is present: `cluster.name` must not contain a single quote or a backslash, and the named cluster must exist in `system.clusters`.

The checks that name an `Atomic` database, a `Replicated` database or the database's own cluster apply with `create_schema: true` and to the `clickhouse-schema apply` command. With `create_schema: false` on an `Atomic` database the operator owns the statements and their delivery, and Jaeger runs only the checks of the named cluster and of the macros.

The checks infer the setup from system tables, and an inference can be wrong for a deployment that this RFC did not foresee. A setting therefore lets an operator overrule them:

```yaml
extensions:
  jaeger_storage:
    backends:
      some_storage:
        clickhouse:
          create_schema: true
          setup_validation: warn    # default: enforce
```

With `enforce`, a failed check stops startup. With `warn`, Jaeger logs every failed check at every start and continues. The setting covers the checks listed as "Refuses to start" in this section. It does not cover three checks whose failure ClickHouse would repeat on the first statement: the check of `cluster.name` for quotes, the existence of the named cluster, and `keeper_path` on a `Replicated` database. It does not cover the refusals of §5.3 about pending schema versions either.

### 6.5 Setup 1: single node

```yaml
table_engine:
  merge_tree: {}
```

One node holds all data in tables of the `MergeTree` family under the public names. The database is an `Atomic` database, or a `Replicated` database with one node.

Jaeger validation:

- **Refuses to start:** the database is a `Replicated` database with more than one node. Every node would get its own unconnected tables. The deployment is setup 2.
- **Refuses to start:** a `cluster` block is present. A single node has no cluster.
- **Refuses to start:** `addresses` lists more than one address. If the addresses are different nodes, each node would hold only the rows that it received. A single node needs one address.
- **Cannot detect:** several nodes with `Atomic` databases behind one address, such as a load balancer. Each node then holds only the rows that it received, and a trace is found on one node and not on another.

### 6.6 Setup 2: replicas only

```yaml
table_engine:
  replicated: {}
```

Several nodes each hold a full copy of all data in tables of the `ReplicatedMergeTree` family under the public names. The database is a `Replicated` database, which delivers every statement to all nodes, so the configuration has no `cluster` block. There are no `Distributed` tables, and a reader or writer can use any node.

Jaeger's configuration is not enough for this setup. The ClickHouse administrator sets up the following on the ClickHouse servers before Jaeger starts:

- Keeper.
- A `Replicated` database on every node, created under the same database name, with the same Keeper path, the same `shard_name` and a different `replica_name` on each.
- The `shard` and `replica` macros on every node, defined before Jaeger creates its tables. The `shard` value is the same on all nodes, and the `replica` value is different on each. Using the database's `shard_name` and `replica_name` as the values keeps the two in step:

  ```yaml
  macros:
    shard: shard1
    replica: replica1
  ```

The replicas of one table find each other in Keeper through a path that they share, and each registers there under its own replica name. In a `Replicated` database ClickHouse chooses both for every table: the path `/clickhouse/tables/{uuid}/{shard}` and the replica name `{replica}`, where `{uuid}` is the table's identifier, which the database makes the same on every node. ClickHouse stores the path with `{shard}` and `{replica}` unexpanded and fills them in each time it loads the table.

The macros are required although a deployment without them appears to work. When a table is created, ClickHouse fills `{shard}` and `{replica}` from the database's `shard_name` and `replica_name` if the node has no macros, and the tables replicate (test A.2). When the node restarts, ClickHouse fills them from the macros only, and without macros every replicated table fails to load with `No macro 'shard' in config` (test A.8). With the macros defined, the tables load after a restart and replicate (test A.8).

Jaeger's `replicated` block is empty in this setup. A `Replicated` database rejects a table whose engine names its own path (test A.2), so the `keeper_path` and `replica_name` fields of the block apply to an `Atomic` database only.

Jaeger validation:

- **Refuses to start:** the database is an `Atomic` database and `create_schema` is true. Jaeger's statements would reach one node only.
- **Refuses to start:** the database's own cluster has more than one shard. The shards would have no `Distributed` table over them. The deployment is setup 3a.
- **Refuses to start:** a node lacks the `shard` or the `replica` macro. Its tables would fail to load after its next restart.
- **Refuses to start:** two nodes have different `shard` macros, or two nodes have the same `replica` macro. The first leaves them with separate copies, and the second makes them claim one replica.
- **Refuses to start:** a `cluster` block is present. It would create `Distributed` tables, which one shard does not need.
- **Refuses to start:** `keeper_path` or `replica_name` is set in Jaeger's `replicated` block. The database would reject every `CREATE TABLE`.
- **Refuses to start:** the server settings `default_replica_path` or `default_replica_name` differ from the ClickHouse defaults. Jaeger cannot then work out which nodes share a Keeper path.

### 6.7 Setup 3a: shards with replicas

```yaml
table_engine:
  replicated: {}
  cluster:
    name: my_cluster
```

The database is a `Replicated` database, which delivers every statement to all nodes. The `cluster` block is what makes Jaeger create the storage tables and `Distributed` tables described below, and `name` is the cluster that the `Distributed` tables forward to. The block has no other effect, so it has no further fields.

Each of the six tables exists twice on every node. The storage table is a table of the `ReplicatedMergeTree` family named `<table>_local`, and a `Distributed` table carries the public name, so the reader and the writer use the same names in every setup. The materialized views read `spans_local` and write `<table>_local`. ClickHouse runs a materialized view when rows are inserted into its source table, on the node that stores them, and not when a replica later copies those rows.

The sharding key of a `Distributed` table decides which shard receives a row:

| Table | Sharding key | Reason |
| --- | --- | --- |
| `spans` | `cityHash64(trace_id)` | All spans of a trace are stored on one shard. |
| `trace_id_timestamps` | `cityHash64(trace_id)` | The view writes each row on the shard that stores the trace, and the key states the same placement. |
| `dependencies` | `cityHash64(timestamp)` | The writer inserts through the `Distributed` table, and the rows of one timestamp are stored on one shard. |
| `services`, `operations`, `attribute_metadata` | none | Nothing inserts through the `Distributed` table. Only the views write to the storage tables. |

A `Distributed` table is created with the cluster, the database and the storage table that it forwards to, and its sharding key:

```sql
CREATE TABLE spans AS spans_local
ENGINE = Distributed('my_cluster', currentDatabase(), 'spans_local', cityHash64(trace_id))
```

The second argument is the database in which the `Distributed` table looks for `spans_local` on the other nodes. Jaeger writes `currentDatabase()` there, a ClickHouse function that returns the database of the connection. The `Distributed` table therefore points at the database that it is created in, also when Jaeger's `database` setting is empty and the connection uses the user's default database. ClickHouse evaluates the function once, at creation, and stores the name. With an empty second argument the table would look in the default database of the user on each remote node, which is not necessarily Jaeger's.

A `Distributed` table by default queues an insert on the node that receives it and forwards the rows in the background. Jaeger sets `distributed_foreground_insert = 1` on its inserts, so an acknowledged insert is stored on its shard.

Jaeger's configuration is not enough for this setup. The ClickHouse administrator sets up the following on the ClickHouse servers before Jaeger starts:

- Keeper.
- A `Replicated` database on every node, created under the same database name, with the same Keeper path, the same `shard_name` on the replicas of one shard and a different one on each shard, and a `replica_name` that is different on each replica of a shard.
- The `shard` and `replica` macros on every node, as in setup 2. Here the `shard` value is the same on the replicas of one shard and different between shards, so that the replicas of a shard share a Keeper path for each table and the shards do not. The `replica` value is different on each replica of a shard.
- A cluster in `remote_servers`, defined identically on every node, that groups the nodes into the same shards as the macros and sets `internal_replication` to true. Without that setting the `Distributed` table writes every insert to every replica of the shard, in addition to the copy that replication makes, and every row is stored twice (test A.5). The definition has to be identical because a `Distributed` table selects the shard by position and weight in the node's own copy of it.

`cluster.name` names this cluster and not the database's own cluster, because the database's own cluster leaves `internal_replication` off by default (test A.5). A `Replicated` database has a setting of its own that turns it on, which would make the separate cluster unnecessary. That variant has not been run (§10).

Jaeger validation:

- **Refuses to start:** the database is an `Atomic` database and `create_schema` is true.
- **Refuses to start:** the named cluster does not set `internal_replication`.
- **Refuses to start:** a node lacks the `shard` or the `replica` macro.
- **Refuses to start:** the named cluster does not group the nodes into the same shards as their `shard` macros, or two replicas of one shard have the same `replica` macro. All nodes with one `shard` value copy each other's rows, so a named cluster that divides them into two shards stores every row twice (test A.6).
- **Refuses to start:** the nodes do not hold the same definition of the named cluster. Two nodes would send the same trace to different shards.
- **Refuses to start:** the named cluster does not list the same nodes as the database's own cluster, or a node lacks the database under Jaeger's name. A node outside the database would receive rows and have no tables.
- **Refuses to start:** `keeper_path` or `replica_name` is set in Jaeger's `replicated` block, or the server settings `default_replica_path` or `default_replica_name` differ from the ClickHouse defaults, as in setup 2.
- **Refuses to start:** the database is a `Shared` database. The engines that ClickHouse Cloud lists as supported do not include `Distributed`.

### 6.8 Setup 3b: shards without replicas

```yaml
table_engine:
  merge_tree: {}
  cluster:
    name: my_cluster
```

This setup has the tables, sharding keys and insert setting of setup 3a, with storage tables of the `MergeTree` family. The ClickHouse administrator sets up Keeper, which the database needs although the tables do not, a `Replicated` database on every node with the same Keeper path and a different `shard_name` on each, and a cluster in `remote_servers`, defined identically on every node, that lists each node as one shard. The tables need no macros, and they load after a restart without them (test A.7).

Jaeger validation:

- **Warns:** at every start, that the data has no second copy.
- **Refuses to start:** the database is an `Atomic` database and `create_schema` is true.
- **Refuses to start:** a shard of the named cluster has more than one replica. Nothing copies rows between the replicas, so one that misses an insert is never repaired. The deployment is setup 3a.
- **Refuses to start:** the nodes do not hold the same definition of the named cluster.
- **Refuses to start:** the named cluster does not list the same nodes as the database. A node outside the database would receive rows and have no tables.

### 6.9 Setup 4: shared storage

```yaml
table_engine:
  merge_tree: {}
```

This is ClickHouse Cloud. Every database is a `Shared` database, and every table is stored once, whatever the number of nodes. The service substitutes the `SharedMergeTree` family for the `MergeTree` family, and the database delivers every statement to all nodes. `replicated: {}` is accepted as well and produces the same tables.

Jaeger validation:

- **Refuses to start:** a `cluster` block is present on a `Shared` database.

## 7. Upgrading an Existing Deployment

An existing deployment has the objects created by a release before this mechanism and no ledger. A binary that carries only version 1 starts against it as before and writes nothing. The first start of a binary that carries version 2, the ten OTLP columns as an automatic version, behaves as follows:

- With `create_schema: true`, the runner creates the ledger, applies and records version 2, and starts. No operator action is needed.
- With `create_schema: false`, the binary fails to start and prints the instructions. The operator obtains the statements and the ledger inserts from `clickhouse-schema plan`, or runs `clickhouse-schema apply`, before the rollout. The release notes say so, because this is the one release in which an operator-managed deployment has to create the ledger table.

A deployment with several nodes on an `Atomic` database is refused by the startup checks of §6 if it runs with `create_schema: true`, whatever versions are pending. It moves to `create_schema: false`, where its operator applies the plan on every node, or to a `Replicated` database. Jaeger cannot count the nodes of an `Atomic` database, so the refusal also meets a single node that uses `replicated` with `create_schema: true`. That deployment sets `setup_validation: warn` (§6.4).

Nothing in an upgrade touches an object or property that the version does not name. A hand-tuned setting, an operator's skip index, a customized codec and the hoisted columns stay as they are. A `ttl` changed in the configuration since the tables were created is likewise left alone by every version that issues no `MODIFY TTL`.

Missing grants are the most likely reason for an upgrade with `create_schema: true` to fail. A Jaeger user with only the `CREATE TABLE` grant needed by today's startup fails to start, because the runner also needs `INSERT` on the ledger and `ALTER` on the tables. A cluster needs `REMOTE`. A self-hosted `Replicated` database with a password on `default` needs a `collection_name` with cluster credentials (§5.6). The release notes list these requirements before the upgrade, and the startup error names the missing one.

The PR that delivers each version updates RFC 0017. An operator who declines part of an operator version, such as the type change, records the version by hand and owns the difference.

## 9. Limitations

- **Two releases starting at once against a database two or more versions behind.** A codec, setting, TTL or view query can keep the value of the older version while the ledger records the newer one. No column or index is lost. `clickhouse-schema apply --reapply-from` repairs it (§5.5).
- **Two releases starting at once against an empty database.** The ledger can record a version that nothing applied, an operator version included. The same command repairs it, and creating a database with one release avoids it (§5.5).
- **A node that is down during an automatic upgrade.** It accepts connections before it has applied the queued DDL, and an insert routed to it in that window fails. A pre-upgrade `apply` job avoids the window (§5.6).
- **Several nodes on an `Atomic` database.** Jaeger does not create or upgrade the schema there. The operator sets `create_schema: false` and applies the plan on every node (§6). An existing deployment that used `replicated` with `create_schema: true` on an `Atomic` database has to change to this, or move to a `Replicated` database.
- **A node that holds the only copy of a ledger row and is down.** Another binary sees the file as pending and executes it again. For an automatic file this is harmless. An `apply` job runs when every node is up (§5.3).
- **Detection of ClickHouse Cloud.** Jaeger recognizes a `Shared` database by the `engine` column of `system.databases`. This follows the ClickHouse documentation and has not been run against a ClickHouse Cloud service. A service created before the `Shared` engine may report `Replicated` there. Jaeger then treats it as a self-hosted `Replicated` database and accepts a `cluster` block. That ClickHouse Cloud rejects a `Distributed` table is also taken from its list of supported engines and has not been run.
- **Wrong detection in general.** A startup check of §6 can refuse a deployment that works. `setup_validation: warn` overrules the checks (§6.4).
- **What has not been run.** Appendix A records the ClickHouse statements that were run for setups 2, 3a and 3b on a four-node cluster. Jaeger itself has not been run on a multi-node setup, and ClickHouse Cloud has not been tested. Test 7 is the first run of Jaeger on these setups.
- **Customized replica paths.** Jaeger refuses a deployment whose `default_replica_path` or `default_replica_name` is changed, although such a deployment can be correct. `setup_validation: warn` admits it (§6.4).
- **ClickHouse Private.** Its documentation confirms `SharedMergeTree` and does not say whether its databases use the `Shared` engine, so setup 4 is confirmed for ClickHouse Cloud only.
- **Databases created by v2.17 or earlier.** They are not version 1 and no delta converts them. The backend refuses to start, and the tables have to be created again (§5.1).
- **Patch releases.** Versions are issued on `main`, so a schema fix cannot ship in a patch release without taking a version number that `main` has already given to other content. A fix that needs a schema change waits for the next minor release (§5.1).
- **A rollback between two trunk builds.** If the open version's file for an object changed between the builds, the older build finds its checksum unrecorded. With `create_schema: true` it executes its older file again, and with `create_schema: false` it refuses to start. Released versions are closed and not affected (§5.3).
- **Interrupted operator versions.** A file is re-executed from its first statement. Statements that are not repeatable depend on the recovery steps in the procedure document (§5.2).
- **A column that already exists under another definition.** `ADD COLUMN IF NOT EXISTS` and the verification check a column by name. A column that an operator created under the name of a later Jaeger column, with another type, is recorded as applied (§5.6).
- **Tested configurations.** The equality test covers the configurations listed in §5.7. A delta that renders wrongly only under an untested combination of parameters passes CI.
- **Drift.** The ledger records what Jaeger applied. It does not reveal a change made outside Jaeger (§10).

## 10. Open Questions

- **A softer rule for optional operator versions.** The binary fails to start on any pending operator version (§5.3), including one whose change the binary does not need, such as a type change for compression. A version could declare itself optional, in which case the binary would start and warn. This reintroduces a database that is behind the binary's versions, so it is deferred until the strict rule proves too costly in practice.
- **A lock for `clickhouse-schema apply`.** A `KeeperMap` table with `keeper_map_strict_mode = 1` can serialize two simultaneous `apply` runs on servers that offer it (§2.4). It cannot revoke distributed DDL that a previous holder queued, so it would be a guard rail and not a guarantee. It is deferred until two operators running the command at once is an observed problem.
- **How old a database an upgrade supports.** Every closed version stays in the equality test and in the binary. A stated limit, such as the versions of the last year of releases, would let older deltas and snapshots be deleted.
- **The database's own cluster for `Distributed` tables.** A `Replicated` database has an `internal_replication` setting. With it, `cluster.name` could be the database's own cluster, and setups 3a and 3b would need no cluster in `remote_servers` and no check that two clusters agree. This has not been run.
- **Drift diagnostics.** The ledger does not reveal a difference made outside Jaeger, such as a `ttl` changed in the configuration after the tables were created. A `clickhouse-schema diff` command that compares the live `create_table_query` of each object with the rendered templates would report such differences without acting on them. It is deferred until there is demand, and nothing in this design prevents adding it.
